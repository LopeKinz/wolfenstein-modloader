In plain wordsIn einfachen Worten

This report surveys the effect definitions of Wolfenstein II: The New Colossus: particles, muzzle flashes, bullet impacts, blood streaks, gore wounds and explosions. A fresh count found 1,781 definitions in 12 types, all readable, and size, colour, particle count and lifetime are plain editable values; the chain from weapon to ammo, projectile, impact, effect and particle was followed on the pistol. Two small text-only mods, bigger grenade explosions and a blue muzzle flash, passed the loader's real patch step. All new work here is static: whether the game actually uses an edited particle or effect definition is still open and was not tested in game, while in The New Order such particle edits were already measured to be ignored.

  • 1,781 definitions in 12 effect types (corrected from 1,861) all parse without error; 797 of them are particles and 265 are effect compositions.
  • Size, colour, count and lifetime edits read back correctly after editing, and whole sub-blocks can be replaced to add fields the original lacks.
  • Retail already mixes weapons: the pistol's muzzle flash uses a battle-rifle texture and the shotgun uses SMG and battle-rifle particles, so new looks can reuse existing textures.
  • Most typical edits (22 of 25) fit into the existing archive space without a rebuild, and both mods ran through the loader's real patch path with 0 errors.
  • Open: whether the game loads edited particle and effect definitions; the code structure points to yes, but nothing was tested in game, and in The New Order particle edits are proven to be ignored.

Answer in one paragraph

TNC's FX surface is twelve TEXT decl types, all in the key = value; dialect (none affected by decl.py's one known weakness, the "key value" list-as-punctuation misparse that only hits material/renderParm/ table/env/json/articulatedFigure): fx (265, an event composition — FX_PARTICLE/FX_DECAL/FX_LIGHT/FX_SOUND/FX_RIBBON/ FX_BLUR_GAUSSIAN events keyed to trigger strings like FX_WEAPON_START_FIRE, each with its own size/duration/tagNames and a reference to the next layer), particle (797, the actual multi-stage particle system — size, color, count and lifetime are direct scalar/vector fields on every stage), projectileImpactEffect (156, the per-surface material impact table — concrete/metal/wood/flesh/glass/... each with its own decal-texture array, decal size, particle refs and sound), ribbon (101, blood/smoke streaks — material, lifespan, two colors, two widths), gorewounds (383, inline RGB color + decal size + size + per-piece spawn/joint data for a wound type), goreBehavior (41, the probability table that picks a gorewounds entry), plus explosion (11), envexplosion (11, explosion spread composition), propExplode (4), particleStage (1), flare (9) and ebolt (2). Fresh census this round, all 12 types, 1,781 decls total (1,812 incl. the two not-fully-censused goreGraph/goreMannequin types, now field-censused too, §1/§9), 0 DeclError under decl.py. Size, color, particle/spawn count and lifetime are all directly editable scalar fields in particle and gorewounds (proven this round by parse→edit→reparse roundtrips, not just inspection); the whole weapon→projectile→impact→fx→particle chain is walkable string references (projectileDecl, impactEffectTable, particle, declPrt), confirmed end to end on the pistol. New effects from existing textures: yes, today, without the still-prototype "new decl name" tool — any particle/fx stage's material/decalMtr/lightMtr field is a plain string naming any already-loaded texture/material, and retail itself already cross-references weapons this way (the handgun's own muzzle flash reuses textures/effects/particles/weapons/battleriflemuzzleflash_front), so a full-body rewrite of an existing decl's content — the same "file" full-replace mechanism gore_realistisch already ships — can recompose any combination of existing materials into a "new" effect under a reused name. Not proven this round: that TNC actually loads an edited particle/fx decl at runtime (no game launch; docs/moddingflaeche-tnc.md already flagged this as open) — narrowed, not closed, by two new static findings (§6): TNC's RTTI shows particle/fx/gorewounds/etc. are handled by the same generic C++ decl template as already-runtime-proven types like weapon/damage, and TNC's install has no TNO-style precompiled generated/*.bin shadow tree that could explain a silent discard. Proven NOT to work in TNO: particle payload edits are silently discarded there (measured: idFile_RingBuffer skip-messages, 35 vs 0 baseline) — only the reference to which particle plays is editable in TNO.

2. particle: size, color, count, lifetime are direct fields

python re_probes/fxdecls/census.py fields particle (797 decls, every scalar leaf, index positions normalized) shows two parallel particle systems living in the same decl type — an older CPU system that dominates the corpus, and a newer GPU system:

Legacy CPU system (edit.stages.item[N].*, by frequency):

  • Size: size.size.size[M].val0/val1 (+ variance, calcType), size.aspectRatio.val0/val1
  • Color: colorAttributes.baseColor.baseColor[M].val0/val1 (RGB, one channel per M), colorAttributes.fadeColor.{x,y,z}, colorAttributes.brightness.val0/val1
  • Count: systemProperties.totalParticles, systemProperties.cycles
  • Lifetime: systemProperties.particleLife.val0/val1 (+ .variance), systemProperties.deadTime.val0/val1, maxSystemDuration (top-level, the whole system's cap)
  • Texture: systemProperties.material — a plain string naming any already-loaded texture/material, e.g. "textures/effects/particles/liquid/splash_lit"
  • Also present: gravity.gravity.val0/val1, acceleration.*, speed.*, offset.*, texAnimation.{numColumns,numRows,rate,type} (sprite-sheet flipbook playback), orientation.type (POR_AIMED/POR_X/…), bounds.b.b[0/1].{x,y,z} (the system's reported AABB — grown bounds with grown size, else particles get frustum-culled early, a real failure mode to watch for in a "bigger" mod).

Newer GPU system (systemPropertiesNEW/colorNEW/sizeNEW/ gravityNEW/velocityFieldNEW/collisionNEW, co-existing in the same corpus, example textures/effects/particles/gpu_spark_add): systemPropertiesNEW.maxParticles/.maxGpuSpawnedParticles/ .maxSpawnedParticles/.cpuSpawnRate/.lifeTime.val0/val1/.emissive/ .bounds.{x,y,z}, colorNEW.initialColor/.finalColor/.opacity/ .overbright, sizeNEW.size.val0/val1.

Proven this round (re_probes/fxdecls/census.py + an ad-hoc roundtrip script, not kept as a separate file beyond the scratchpad): edited particle:weapons/handgun/handgun_muzzleflash — size ×3 (edit.stages.item[0].size.size.size[0].val0/val1 → 0.6), brightened color (colorAttributes.baseColor.baseColor[1].val0 → 1.0), tripled count (systemProperties.totalParticles → 3) — Decl.set() then .render() then a fresh Decl() on the output: re-parses without error, every edited value reads back correctly. Same for particle:weapons/grenades/frag/frag_explosion's maxSystemDuration. This proves the edits are structurally safe (same class of proof as the project's existing "1,432/1,432 roundtrip" test in docs/moddingflaeche-tnc.md §2.2, just scoped to this round's 3 types) — it does not prove the game loads them, see §6.

3. fx: the event composition, and a proven block-level insert trick

fx decls (edit.editEvents.item[N]) are the layer every weapon/breakable/ cutscene points at. Fields seen across 264 parsed decls: name, group, type (FX_PARTICLE/FX_DECAL/FX_LIGHT/FX_SOUND/FX_RIBBON/ FX_BLUR_GAUSSIAN/FX_SCREEN_SHAKE per TNO's moddingflaeche-tno.md §2.9), duration, delay, fadeInTime/fadeOutTime, size (yes — fx events carry their own size override, independent of the referenced particle's own size), looping, tagNames (joint names on the owning .md6 model, e.g. "muzzle", "fx_righthand"), multiTagUseType, startCondition/stopCondition/suppressCondition (arrays of trigger strings — FX_WEAPON_START_FIRE, FX_WEAPON_START_FIRE_UPGRADE_1, FX_CINEMATIC_N, FX_GENERIC_N, FX_NONE), originType/rotationType/ rotOffsetAngles/offset, and one of four typed parameter blocks: particleParms.declPrt (→ particle decl), decalParms.{decalMtr,depth, angle,isPersistent,priority} (→ a decals/... material, per r4_materials.md), lightParms.{radius,intensity,lightMtr} (→ a lights/... material), ribbonParms.{declRibbon,widthOverTime, alphaMultiplier,...} (→ ribbon decl), soundParms.startSoundEvent.

Concrete, fully walked example — the pistol's muzzle flash:

fx:weapons/handgun
  editEvents.item[0]  name=muzzleflash  type=FX_PARTICLE  tagNames=[muzzle]
                      startCondition=[FX_WEAPON_START_FIRE]
                      particleParms.declPrt = "weapons/handgun/handgun_muzzleflash"
  editEvents.item[8]  name=muzzlelight  type=FX_LIGHT  tagNames=[muzzle]
                      startCondition=[FX_WEAPON_START_FIRE]
                      color = { y=0.521  z=0.184 }           // x omitted (defaulted)
                      lightParms.radius = { x=2 y=2 z=2 }
                      lightParms.lightMtr = "lights/gaus"    // no explicit intensity
  editEvents.item[9]  same, group="elephant" (upgrade variant), has lightParms.intensity=3

particle:weapons/handgun/handgun_muzzleflash itself is two stages ("stage"/"stage1") whose systemProperties.material fields are "textures/effects/particles/weapons/handgunmuzzleflash_side" and — reused from a different weapon entirely — "textures/effects/particles/weapons/battleriflemuzzleflash_front". This is organic, in-retail proof that cross-weapon material reuse in a particle stage is normal and safe, not a modded hack.

A stronger example, found this round: fx:weapons/shotgun's own editEvents reference whole particle decls that belong to other weapons, not just a texture buried inside one particle's own material field —

fx:weapons/shotgun
  editEvents.item[5].particleParms.declPrt = "weapons/smg/smg_shell_ejection_smoke"
  editEvents.item[6].particleParms.declPrt = "weapons/battlerifle/battlerifle_shell_ejection_sparks"
  editEvents.item[8].particleParms.declPrt = "weapons/smg/overheat/shroud_heat_1"

three of the shotgun's own fx events point at smg/battlerifle particle decls by name. Confirmed by reading the live decl's particleParms.declPrt paths directly this round. This is free, in-retail corroboration at the fx-layer (whole-decl reuse) on top of the particle-layer example above (one texture string inside a decl) — the engine itself never treats "weapon X's effect" as owned exclusively by weapon X.

New technical finding this round: wolfsdk/decl.py's Decl.set() works on any addressable path, including a whole nested block, not just scalar leaves — because every path (scalar or {...} block) is recorded as a Value with its own byte span. Proven: replacing fx:weapons/handgun's edit.editEvents.item[8] (the standard muzzle light, which has no intensity field and only a partial color) with a new block that adds intensity = 40, a full color, and radius = 6 re-parses cleanly and reads back every new field correctly. This matters because decl.py's surgical editor cannot otherwise add a field that isn't already present in the retail text (set() raises DeclError if the target path doesn't exist) — block-level replacement is the one way around that without falling back to a full-file "file" replace of the entire (possibly much larger) decl. It is the same "file" mechanism gore_realistisch already uses, just scoped to one sub-block instead of the whole document, which keeps the edit far inside the csize+gap budget (§5).

4. The full chain: weapon → ammo → projectile → impact → fx → particle

Walked on the pistol, every field read directly from the live archive:

weapon:weapon/player/sp/handgun_nomesh
  initialAmmoDecl = "ammo/player/sp/handgun"
ammo:ammo/player/sp/handgun
  projectileDecl = "projectile/player/pistol"
projectile:projectile/player/pistol        (inherits projectile/player/default)
  impactEffectTable = "handgun"
  damageDecl = "damage/firearm/bullet_pistol"
projectileImpactEffect:handgun             (inherits bullet_base -> default)
  fleshEffect.ribbons.item[0].ribbon = "weapon/battlerifle/impact/battlerifle_blood"
  (inherited from "default"): fleshEffect.particles.item[0].particle =
    "weapons/base/impacts/bullet/bullet_flesh"; concreteEffect.decalMaterial =
    [4 existing textures]; concreteEffect.decalSize = 0.2; ... (28 surface types total)
ribbon:weapon/battlerifle/impact/battlerifle_blood
  material = "textures/effects/ribbons/weapons/blood_impact"
  lifespan = 0.5
  ribbonSegment.colorOnSpawn/.colorOnDeath = { r g b }   // RGB
  ribbonSegment.widthOnSpawn/.widthOnDeath = { min max }  // size
fx:weapons/handgun
  editEvents.item[0].particleParms.declPrt = "weapons/handgun/handgun_muzzleflash"
particle:weapons/handgun/handgun_muzzleflash
  stages.item[0/1].systemProperties.{material,totalParticles,particleLife}
  stages.item[0/1].{size,colorAttributes}

Every link in this chain is a plain string field, independently set()-able. The projectileImpactEffect per-surface table (defaultEffect/metalEffect/stoneEffect/fleshEffect/glassEffect/ ...39 top-level edit.* blocks in default, re-counted this round with Decl.paths() rather than eyeballed — pass 1 said "28", see "Pass 1 errors" above; 35 of the 39 literally end in Effect, the rest are hazardFire/hazardSteam/ricketyMetal/ricketyWood) is the concrete "impact effect decl" the task asked for: each surface's decalMaterial is an array of existing decal textures the engine already picks randomly from, decalSize is a bare float, and particles/ribbons are arrays of {groupName, particle|ribbon, translucencyScale, bind}.

Blood/gore chain, walked on a disintegration wound (gorewounds:fullbody/humanoid/disintegrate):

damage:<any firearm decl>.declGoreBehavior = "standard/pistol"
  (63/154 raw damage archive entries carry this field, 62/151 by unique
   decl name — both re-verified this round; pass 1's bare "63/154" read
   as, and numerically collided with, projectileImpactEffect's unrelated
   156/154 row above, see "Pass 1 errors")
goreBehavior:standard/pistol
  probability.item[N].{woundType, probability}      // picks a GORETYPE_*
gorewounds:<decl matching that woundType>
  visuals.goreSpray.sprayFX = "FX_GORE_DISINTEGRATE"          // engine enum string, not a decl ref — open, see §7
  visuals.bloodPool.decalParms.item[0] = { decalMat, size={x,y}, priority }   // existing decal texture + direct size
  visuals.disintegrate.color/.colorScale/.pieceInitialColor/.pieceFadeColor/.pieceColorScale   // inline RGB, no fx/particle indirection
  spawning.spawnEntities.item[N].fxTagJoint = "fx_hips"        // joint tag the spawned gore piece's own fx binds to

So gorewounds carries its own inline color/size fields for disintegration effects — no separate fx/particle decl to edit for that specific visual; bloodPool's decal (a literal blood-pool texture) is both size- and texture-swappable directly.

5. Budget: does an edit fit without a 3.4 GiB archive rebuild?

Not re-measured this round — cited from the project's own prior, reproducible measurement (docs/moddingflaeche-tnc.md §4.1, python tools/survey_tnc.py --budget), because it already covers exactly these two types with a real test-edit (every integer in the decl ×1000, re-Kraken'd):

type csize median gap median fits in csize alone fits in csize+gap
fx 852 B 48 B 4/25 22/25
particle 2,633 B 205 B 0/25 22/25

So ~88% of realistic size/color/count/lifetime edits land inside the existing payload slot + its zero-filled gap and patch in place with no archive rebuild (idcl.plan_in_slot()/write_in_place(), already the project's production writer). The ~3/25 oversized ones fall back to a Kraken recompress (§4.3: byte-identical to retail, 401/401 and 194/194 measured) or a mode-0→2 switch (§4.2) — both already proven, not new work needed for this track. The decl.py "vector dialect" weakness (§2.3, 2,242 decls project-wide, only material/renderParm/table/env/ json/articulatedFigure/one renderLayerDefinition/one entityDef) does not include any of the 12 types in §1 — consistent with this round's own 0-DeclError census.

6. PROVEN vs. INFERRED

PROVEN (this round, static/structural):

  • All 1,781 decls across the 12 FX-relevant TNC types parse with decl.py, 0 DeclError (fresh census, not cited from a prior round; 1,812 incl. goreGraph/goreMannequin, also 0 DeclError, §9).
  • particle's size/color/count/lifetime fields and fx's light intensity/color/radius fields are Decl.set()-able scalars that roundtrip (parse → edit → render → reparse → value matches) cleanly.
  • Decl.set() works at block granularity, not just scalar leaves — proven by replacing fx:weapons/handgun's editEvents.item[8] wholesale and having the added intensity field read back correctly after reparse.
  • The weapon→ammo→projectile→impact→fx→particle chain (§4) is real, not inferred — every field and value was read directly off the live pistol decls in this round, not copied from a prior report.
  • Cross-weapon material reuse inside a particle decl's systemProperties. material field is retail-native (handgun's own muzzleflash uses a battlerifle texture), so authoring a "new" effect from only existing textures needs no new tooling, just a full-body rewrite of an existing decl's content.
  • glass/destructiblePiece/impactParticles/impactSounds are absent from TNC's type list (checked against the unfiltered census, not a name guess).
  • The fx:weapons/shotgun cross-weapon reuse (§3) — three of its own fx events point at smg/battlerifle particle decls by name, read directly off the live decl this round.

r_particleFadeQualityMultiplierDurango and r_particlesMinAlphaDurango are two fully separate, independently-registered cvars (pass 1 wrote them as one name with a "(Durango)" qualifier — fixed, see "Pass 1 errors"), not platform-conditional aliases of the base name; both are set the same way (SetCvar in console, or resourceExec for the exposed=false ones below), global quality/distance multipliers, not per-effect size/color controls — a coarse, zero-risk complement to the decl-only levers, not a substitute. - TestFx/TestParticle/StepParticleTime/ai_startfx/ai_stopfx console commands are registered but not exposed (exposed: false in re_probes/cmdtable/commands.json, re-confirmed this round) — same resourceExec <file> -s unlock the TNC console-unlock memory already proved would be needed to reach them. - New static data point on the central open question (below): TNC's RTTI type-descriptor table (docs/ghidra/rtti_tnc.json, 5,783 classes) has a C++ class for every one of 12 of these 14 decl types, and every one is an instance of the same generic template the engine uses for every other ordinary TEXT decl (idDeclDamage, idDeclAmmo, idDeclWeapon, ...): idDeclInfoTemplate<VidDeclParticle>, <VidDeclFX>, <VidDeclParticleStage>, <VidDeclProjectileImpactEffect>, <VidDeclGoreWound>, <VidDeclGoreBehavior>, <VidDeclGoreGraph>, <VidDeclGoreMannequin>, <VidDeclRibbon>, <VidDeclExplosion>, <VidDeclEnvExplosion>, <VidDeclFlare> are all present (propExplode/ebolt, the two smallest types at 4 and 2 decls, have no matching RTTI entry — not investigated further, possibly inlined/devirtualized for such a tiny type). TNO has base/generated/decls/particle/*.bin, a 1:1 compiled mirror of every TNO particle decl, which is the actual mechanism that discards edits there (§6, TNO row above). Checked this round whether TNC's install tree has anything analogous: find ... -iname '*generated*' to depth 4 under the TNC install root finds nothing (only base/{bink,maps,sound,_wolfsdk_tnc}, dlc/dlc_{0,1,2,3,5}, virtualtextures/maps). TNC's closest binary neighbors (prtmeshdist 479 unique, staticParticleModel 7 unique, decalatlas 864 unique) don't 1:1-match particle's 777 unique names the way TNO's generated/particle/*.bin count matches TNO's particle decl count. Doesn't prove TNC loads edits, but removes the one concrete alternative mechanism this round could check for without a game launch.

INFERRED, not proven (needs a real game launch this round could not do):

  • That TNC actually loads an edited particle/fx decl at runtime and the visual changes. docs/moddingflaeche-tnc.md §7 already flagged this exact gap ("particle... ob das Laden auch funktioniert: nicht geprüft" — "particle... whether loading also works: not checked"), and this round narrows it (generic idDeclInfoTemplate RTTI finding, no generated/*.bin-style shadow directory, both above) without closing it — this is still the single open item that decides whether §2's entire size/color/count/lifetime lever works at all, or whether TNC's particle system turns out to have the same frozen-binary-stream behavior TNO's does. The balance of static evidence now leans toward "loads like any other decl" (TNC's particle/fx decls are unambiguously TEXT and parse cleanly, which TNO's binary .bin streams never were; they go through the same generic C++ decl template as already-runtime-proven types like weapon/damage/ammo; and TNC has no TNO-style precompiled shadow tree) — but none of this is a load-path trace, only structural analogy. The in-game test below is still the only thing that actually answers it.
  • That visuals.goreSpray.sprayFX = "FX_GORE_DISINTEGRATE" in a gorewounds decl is a closed engine enum (not further editable/ listable) rather than a decl reference — read as a bare string, not traced into compiled code this round (one --strings attempt at related FX_WEAPON_START_FIRE* enum strings came back "no references found" in the Ghidra xref search, likely because these are read from a jump/string table rather than a direct lea+cmp call site — not pursued further, see §7).
