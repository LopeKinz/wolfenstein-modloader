In plain wordsIn einfachen Worten

Wolfenstein II: The New Colossus runs its mission logic with Kiscule scripts: node graphs such as "trigger entered, spawn a wave, count kills, complete objective". This page shows that all 3,162 script files of the game can be read and written back byte for byte. It builds a model of the node types, a validator and a first new script from scratch. The new script is structurally valid, but it has not yet been run in the game.

  • All 3,162 script files in the install round-trip byte-exactly.
  • The model covers 83,812 nodes in 209 types; one simple edge rule holds for all 103,687 connections.
  • The validator accepts 2,927 of 2,977 retail scripts (the 50 rejects are known game defects) and rejects all 12 deliberately broken test scripts.
  • A new 11-node script is built: enter the area, a wave of 5 enemies spawns, and 1 second after the fifth kill the objective completes.
  • Two test archives for the Gestapo office map are ready. Runtime is unconfirmed: nothing has run in the game yet.

1. Format and Round-Trip

An extkisclule entry consists of two layers:

  1. compfile (wolfsdk/tnccrypt.compfile_unwrap/wrap). A 16-byte header i64 usize, u64 csize, followed by Kraken on LEVEL_NORMAL. Retail writes a file raw (usize < 0) if Kraken does not make it smaller. This affects the 17 empty scripts. The tool applies the same rule (wrap()) and matches all 3,162 containers byte-exactly.
  2. Decl plaintext. It begins with a line break and ends on NUL. Each line is either key = {, }, or key = value;, indented with a tab per depth. Line endings are LF or CRLF per file. Parser and emitter come from tools/kiscule.py (only imported).

The check compares both levels, text and container. A verification flips a byte and requires the comparison to fail.

2. The Model: Nodes, Connections, Edges, Variables

2.1 Structure

edit = { kiscule = {
    version = 6;                 Retail: 6 (2872), 5 (83), -1 (5), missing (17 empty)
    nodes     = { num; item[i] = Node }
    comments  = { num; ... }     Editor notes, no runtime effect
    variables = { num; ... }     named graph variables
} }

### 2.2 Rules, measured via Retail

* **Connection types.** There are six. For the impulse (flow) they are `InputRegular`, `InputEvent` (one), `OutputRegular`, and `OutputNotification` (out). For values they are `InputVariable` (in) and `OutputVariable` (out). Measured edge types: Value→Value 41 180, Regular→Regular 33 156, Notification→Regular 29 339, plus 12 to `InputEvent`. Other combinations do **not** occur. This is the validator's edge rule.
* **An edge exists at both ends.** The output carries the `endNodeID/endConnectionPointID` of the input and vice versa. The key is the pair (node-ID, connection-ID). The edge `id` is unsuitable for this; it is not identical at both ends (see `docs/kiscule.md` §3.3).
* **Parameters.** Each parameter appears once in the node (`parameters.object`) and can additionally arrive from outside as an `InputVariable` of the same name. An example is `listenedEntities`, fed by an `EntityReference`. Thus, entities hang off event nodes.
* **Actions pass the impulse further.** For every impulse input of an action (`Activate`, `ObjectiveComplete`, `Send` …) there is an `OutputRegular` of the same name. It fires after the action; chains are built over it. Retail uses this for example with `ActionMission.ObjectiveComplete → SendCustomEvent` (49 times).
* **Variables.** The `variables` block contains `idKisculeGraphVariable{Bool 618, Int 279, EntityReference 69, Time 56, Float 35, ListEntityReference 27, EntityDef 2}`. Each variable has the fields `name`, `global`, `isCrossMap`, `defaultValue`, and `value`. It is read and written via `NamedVariable*` nodes with `variableName`. Of these, 2819 refer to a variable of the same file and 22 do not, thus cross-script.
* **Events between scripts.** `SendCustomEvent{eventName, global=true}` → `GetCustomEvent{eventName}`. The mission logic of c2v1 is wired exactly like this (§4.2).
* **Node type = class.** Each of the 209 Retail types is an RTTI class of the EXE. All 388 node and parameter class names appear verbatim in the runtime image `runtime_87400/module.bin`. Further 101 `idKisculeNode*` classes exist in the EXE but are not used in Retail. Whether the engine loads them is untested.

**Assignment of Mission Components from the Order:**

* *Trigger entered* → `TriggerNotification.Touching` with `classFilter = "idPlayer"`. The Trigger Entity is provided via `EntityReference` → `listenedEntities`. For volume, there is `VolumeNotification.Enter`.
* *AI killed* → `AiKilledNotification.Killed`. It fires **per kill**, `victim` provides the corpse. Evidence: Retail counts this per `Counter` up to 22 (`c1v2_challenge`, 22 AI, `endCount` 22).
* *Counter reached* → `Counter.Reached End`.
* *Spawn* → `ActionTrigger.Activate` on an `idTarget_AISpawn` Entity. Retail does this 364 times. The wave consists of the Entities in whose `targets` list they appear. Alternatively, there is `ActionShowHide.Show` on AI (725 times).
* *Objective update/complete/mission end* → `ActionMission` with `ObjectiveStart`, `ObjectiveComplete`, `SetActiveObjective`, `MissionComplete` or `MissionEnd`. For the chapter end in the DLC, `ActionChronicle.End` is added, for map switching `ActionNextMap`.
* *Door open* → **In Retail there is no door node.** `idKisculeNodeDoorNotification` exists only as an RTTI class and is used nowhere. Doors are `idDynamicEntity`/`idProp2`, mostly with `idConstraint_Hinge`. Where Retail moves a door via script, it uses `ParametricTranslation.entity` (118 references to Entities with "door" in the name), `ActionRotateEntity.targets` (50), `KeyframedTranslation` (31), `ActionShowHide` (hide 95, show 92) or a Midnight sequence (`OpMidnightParametersControl.Door`, 18).
* *Sound play* → `ActionSoundPostEvent.Post` with `soundEvent` (Wwise) to `entity`, for speech `ActionSoundVoiceOver2.Play`.

## 3. The Validator

`validate(text, db, entity_names)` in `tools/probe_kiscule_write.py` returns an error list. Empty means valid. It checks the following:

* **Structure.** The grammar, every `num`/`item[]` count, and the NUL at the end. The emitter must deliver the same bytes (canonical). The block sequence is `version/nodes/comments/variables`, where version is a Retail value.
* **Nodes.** At least one (otherwise the runtime message "Kiscule entity '%s' is empty" applies). Node IDs are unique. The type must be known to Retail, the parameter class appropriate, every connection (Name, Type) for this type known, connection IDs unique.
* **Edges.** The target exists (Node and Connection). The edge is recorded at both ends. The Edge Rule Direction/Type applies.
* **Map.** With `entity_names`, every value of an `EntityReference`/`ListEntityReference` must be present as `entityDef` in the target map.

**Positive control.** Across all 2977 Retail scripts, 2927 are clean. The 50 rejections distribute as follows: 25 × edge to empty, 17 × empty, 7 × one-sided, 1 × duplicate connection ID. These are exactly the Retail defects from `docs/kiscule.md` §3.3. The check fails as soon as another class appears or less than 95% are clean.

**Negative controls.** Every mutation of our script must be rejected:

| Mutation | Message |
|---|---|
| **dangling edge, endNodeID is empty** | `Edge 28456371 points to empty: Node 424242 missing` |
| **dangling edge, endConnectionPointID is empty** | `… Connection 424242 to Node 651609970 missing` |
| **unknown node type** (`idKisculeNodeCounterX`) | `unknown node type idKisculeNodeCounterX [67139160]` |
| Back of an edge deleted | `Edge … only one-sided` |
| unknown connection (`ReachedEnd`) | `unknown connection ReachedEnd:OutputRegular` |
| Input to output reversed | `Edge … connects OutputNotification with OutputRegular` |
| `nodes.num` too high by 1 | `Structure: num = 12, but item[11] missing` |
| Entity that does not exist in the map | `Entity 'c2v1_gibtsnicht' does not exist in the map` |
| duplicate node ID | `duplicate node ID 509157573` |
| empty graph | `no nodes …` |
| NUL missing at end | `Structure: no NUL at end` |
| Entity template without `externalKisculeDecl` | `Template does not match (1/0 replacements)` |

## 4. The Minimal Script

### 4.1 Graph (`mission_wave_c2v1.graph.txt`)

EntityReference "c2v1_combat_triggers_trigger_firstarea" ──value──▶ TriggerNotification.listenedEntities TriggerNotification (classFilter idPlayer, max 1) ──Touching──▶ ActionTrigger.Activate EntityReference "c2v1_combat_target_ai_spawn_firstarea" ──value──▶ ActionTrigger.targetEntities ListEntityReference [5 KI of the spawn list] ──value──▶ AiKilledNotification.listenedEntities AiKilledNotification (max 5) ──Killed──▶ Counter.Increment (0 → 5) Counter ──Reached End──▶ Delay.Start (1000 ms) ──Finished──▶ ActionMission.ObjectiveComplete PlayerEnt ──Player──▶ ActionMission.player ActionMission (mission_c2v1_main, obj_01_find, showNotification) ──ObjectiveComplete──▶ SendCustomEvent "start_obj_02" (global)


The script has 11 nodes, 9 edges, 30,591 bytes of text, and 3,361 bytes of payload (`mission_wave_c2v1.extkisclule`, sha256 `4eae4d81…d532`). The build is reproducible because the IDs are deterministically derived from a seed.

**How it is created.** Every node is a copy of a real Retail node of the same type, with the most common connection count, full connection list, and `properties`/`visible` as in the game. New are IDs, parameters, and edges. The class `Script` (`add`, `link`, `render`) is the write API: `link()` records every edge at both ends.

### 4.2 Why exactly so – Retail evidence, each as a test

* **Each of the 9 edges is a Retail edge pattern**, counted as (Type.Connection → Type.Connection):
  EntityReference→TriggerNotification 1562, Touching→ActionTrigger.Activate 176,
  EntityReference→ActionTrigger.targetEntities 660, ListEntityReference→AiKilled 62,
  Killed→Counter.Increment 43, Counter.Reached End→Delay.Start 16,
  Delay.Finished→ActionMission.ObjectiveComplete 11, PlayerEnt→ActionMission.player 220,
  ObjectiveComplete→SendCustomEvent 49. *The direct edge Counter→ObjectiveComplete does not exist in Retail (0). The check therefore failed in the first version, and the Delay node was included.*
* **The Retail script `c2v1_combat_kiscule_firstarea` remains unchanged within it.** It consists of Trigger → Spawn target, with identical types, identical parameters, and 3 identical edges. Retail does exactly this at this point. We only attach the kill branch.
* **The counting pattern originates from Retail.** `maxNotificationCount` = number of listed KIs = `Counter.endCount` appears in 10 Retail cases (`gp073 hangarfight` 2, `c1v1_combat` 4, `c1v2_challenge` 22, …).
* **Spawn and death counting in the same script.** 13 Retail scripts fire an `idTarget_AISpawn` and listen for its KI via `AiKilledNotification` (`cb_kiscule_horton` 8 KIs, `combat_streets` 10, `c3v2_combat_enter_trainstation` 14, `c2v3_combat_kiscule` from the same DLC …). This is our pattern.
* **The wave.** `c2v1_combat_target_ai_spawn_firstarea` is an `idTarget_AISpawn` with 5 KIs in `targets`. In the installed override, 3 of them are switched to `elite_heavy`, but remain `idAI2` with the same names. The kill notification goes via the name, so this fits.

### 4.3 The Retail mission chain in c2v1 – and why the test would otherwise show nothing

`sacramento_gameplay_kiscule_c2v1.decl` runs the mission. The following chain is measured and recorded as a check:

BeginGame → Delay 500 → ActionMission.MissionStart (4 targets) → Delay 4100 → Send "start_obj_01" → Get → ActionMission.ObjectiveStart(obj_01_find) Trigger "sacramento_gameplay_triggers_obj_1_complete".Touching → Send "end_obj_01" → Get → ActionMission.ObjectiveComplete(obj_01_find) → Send "start_obj_02" → …


This Retail trigger is located at (−4.75, −193.75), **approximately 11 units** next to our wave trigger at (−14.45, −199.30). The enemies stand behind it (y −172 … −193). The player would thus fulfill "Enter the offices" already upon entering before the wave is dead, and our script would remain invisible.

**Therefore both candidates contain a second, minimal intervention.** In the mission script, exactly one `TriggerNotification` node (ID 1728583878) is set from `enabled = true` to `enabled = false`. Only this single line changes, which has been verified. Our script takes over the continuation that Retail makes at that same point: after `ObjectiveComplete`, it sends `start_obj_02`. It has also been verified across all scripts binding the c2v1 map:

* `end_obj_01` is sent by only this single node and receives only from the Retail fulfiller. No other script loses anything.
* `start_obj_02` listens only to the mission script.
* After the intervention, the Retail path is dead, and **our script is the only active fulfiller of obj_01**. This is read in the built chunk.
* A second disabling is rejected as a negative control.

(Initially, the check also counted scripts from other maps, `c2v2` and `c2v1_custom`, and failed. Now it counts only scripts binding the map via `externalKisculeDecl`.)

## 5. Name binding: how a script comes to execution

Across all 39 Retail `.entities`:

* All **3020** `idKisculeEntity` entities reference a script via `edit.externalKisculeDecl`. Inline Kiscule does not occur, nor do `targets`.
* Each reference resolves to exactly one extkisclule entry: 3000 exact matches, 20 case-insensitive. The entry name is the Decl name.
* Per map (36/36 with readable `.mapresources`), the extkisclule lines in `.mapresources` are precisely the lowercase references. A new script therefore requires **one new MRL line**.
* The 24-byte field of each MRL line is the layer mask of the binding entity (2761/2761). Bit i corresponds to Layer i of the MRL layer list. Without a layer, only bit 191 is set (`…80`), causing the script to always load.

A new script binds using this entity (`entity_binding_example.txt`). It is the Retail entity `c2v1_combat_kiscule_firstarea`, with only Name and Decl changed:

entity { entityDef mission_kiscule_wave_1 { inherit = "kiscule"; class = "idKisculeEntity"; expandInheritance = false; poolType = "POOLTYPE_NONE"; poolGranularity = 2; edit = { soundParms = { enableQuickSave = true; noOcclusion = true; } spawnPosition = { x = -1.1000000238; y = -195.200088501; } externalKisculeDecl = "maps/game/dlc/c02/c2v1_mission/kiscules/mission_kiscule_wave_1.decl"; } } }

```

This includes an extkisclule entry with exactly this name (lowercase) and the MRL line (extkisclule, <name>, LayerMask) in generated/buildgame/game/dlc/c02/c2v1.mapresources.

What should be visible in-game (normal mission start c2v1):

  1. After approximately 4.6 s, "Enter the offices" appears as usual.
  2. Enter the first area. The wave appears as in Retail; there are five firstarea enemies.
  3. Upon entering the offices, the objective is no longer fulfilled.
  4. Approximately 1 s after the fifth kill of the wave, "Enter the offices" is fulfilled, and the next objective (obj_02) begins.

Evaluation: Point 4 confirms Script Binding, AiKilled/Counter, and ActionMission. If the objective is never fulfilled, our script did not run, or the branch under AiKilled does not contribute, and the mission remains stuck at Objective 1. If the wave does not appear, the trigger part did not run already. If the objective is fulfilled upon entering the offices, the intervention into the mission script was not loaded. Test B only if A works. Then B separates "Exchange Content" from "Bind New Script".

7. What Is Not Proven

  • Runtime. None of this ran in-game. All statements are structural or derived from Retail patterns.
  • ObjectiveComplete on an objective that has not yet started. The objective starts 4.6s after map start; killing five enemies in less than 3.6s is hardly possible. What the engine does in that case is unmeasured.
  • version = 5/6/-1, the properties bits 1/4/32, and the edge id. They are copied from templates; their meaning is open (see docs/kiscule.md §9).
  • The 101 unused node classes of the EXE (including DoorNotification, LogicGateAnd, HudTimer). Whether the engine loads them is untested.
  • Custom Objective Text/Objectives ("Eliminate the officers") require new missionobj Decls and Strings. This is not part of this track; see re_probes/missions/text/. Our script uses the existing objective cobalt/c2v1/mission_c2v1_main_obj_01_find.
  • 3 Retail maps have a .mapresources in a different layout. The binding rule was not recalculated there.
