In plain wordsIn einfachen Worten

This report studied the dynamic lights of Wolfenstein II: The New Colossus: one engine class covers every light type (point, spot, probe, area and others), and the look of a light comes from one reusable light material. Reading the game's data and settings suggests that a new light adds its glow on top of the baked lighting of walls and furniture instead of being ignored by it. The custom kit map already has 12 new lights built and installed, and a much cheaper test with the hidden addLight command is proposed. Everything here is static analysis: the counts and file checks are proven, but the main claim is only inferred and no light was seen in the running game.

  • All 13,406 placed lights on 39 maps use one engine class; the light type is just one text field (5,903 spot, 4,413 point, 2,529 probe lights).
  • 133 existing light materials can be reused with a plain text edit; whether a brand-new light image can be added is still open.
  • No setting caps the total number of lights; the budgets are a light grid of 3,072 cells (16 x 8 x 24), per-frame culling and throttled shadow updates. Correction: 9 light settings, not 2, have no cheat flag.
  • The kit map's 12 lights (9 point, 3 spot) are copies of two real game lights; the built file is installed but has not been loaded in the game yet.
  • Open: whether a new light really reaches surfaces with baked lighting; the hidden addLight command, run via resourceExec in any level, is a cheap first test that has not been run.

Round-6 research pass on dynamic lights in The New Colossus: which C++ classes and decl fields make up a light, which budgets and limits the engine enforces, and whether a new light can light the new geometry of the custom kit map. idLight turns out to be the one class behind every light type, falloff and projection both come from one lightMaterial, and the GPU light list is bound once per frame with view scope, so a new light should add to the baked lightmap of kit pieces rather than replace it — inferred from the decl/renderParm/cvar architecture, not proven at instruction level, and never seen in the running game. The kit map's 12 lights are already built and installed; a cheaper console test (addLight through the resourceExec route) is proposed at the end. Everything below was read-only; no game was launched.

Answer in one paragraph

idLight is the one C++ class behind every dynamic light type (point, spot, probe, area, scattering, and — once, corpus-wide — parallel); the light/point/light/spot/light/probe decls set nothing but lightType, so every other default (whether a light casts shadows, which falloff image it uses, …) is a C++-side default, not a decl default. A light's falloff and its projected "cookie" texture are both named in one material decl via lightMaterial (74% of corpus lights set it explicitly; 133 distinct retail lights/... materials exist to reuse, each naming a lightfalloffmap and a lightprojectmap, both packed into one shared light image atlas — idLightAtlasResource, sized by r_imageAtlasLightWidth x r_imageAtlasLightHeight, default 2048x1024). Whether a new light can light the kit's new geometry: the GPU-side light list (lights, a StructuredBuffer<light_t>, and its per-cluster index buffers clusterLightsId/clusterNumLights) is declared with view scope — bound once per frame, not per-material — and lightmask (the one renderParm that could exempt a surface from it) is never set away from its default (1) by any of the 11,469 census'd retail materials. That is code-level (renderParm-scope) evidence, not a guess, that dynamic lights are a frame-global resource every forward-shaded surface samples, independent of which "ambientprogram" variant (lightmapped "Unique" or not) a material picked — so a new idLight placed near the kit's idStaticInstanceEntity pieces should light them on top of whatever ambient/lightmap term r2_maplightstairs.md's variant H gives them, not instead of it; nothing found disables dynamic lighting for lightmapped statics. This is INFERRED from decl/renderParm/cvar architecture, not instruction-level proven — no shader bytecode decompiler exists in this toolkit (same limit r4_materials.md already recorded) and it has never been seen in the running game. The recipe already exists and has already been executed: tools/design_kitmap.py's LIGHTS list + tools/build_kitmap.py's donor-transplant light authoring placed 12 idLight entities (9 point, 3 spot) into the kit map by cloning two real retail c2v1 lights — which means each new light inherits a complete, retail-precedented lightMaterial/ castShadows/shadowZControl configuration, not a blank one — and tools/build_kitmap_variant.py H folds that .entities text together with the lightmap/stairs/collision fixes into one container that is currently installed live at dlc/dlc_0/base/chunk_22.resources (sha256 cd7e9340…, byte-identical to re_probes/kitmap/variants/H/chunk_22.resources, independently re-hashed this round). Nobody has loaded it in the game yet.

3. Light materials and falloff/projection images

A lightMaterial decl is an ordinary material decl (same text format as matpipe.md/r4_materials.md already solved), just with a different set of renderParm keys. Example, read whole this round (lights/analytical/point/point_frac80, one of 133 distinct lights/... materials found across the 28-archive census):

lightfalloff2d              1.000000
lightfalloffatlasscalebias  { 0.030273, 0.029297, 0.000488, 0.000977 }
lightfalloffmap              "lights/analytical/falloff_aniso0_r64_frac80_gamma2.tga$pad2"
lightprojatlasscalebias     { 0.006836, 0.013672, 0.000488, 0.000977 }
lightprojectmap               "lights/proj_white.tga$pad2"
lightsatlasmap               _lightimageatlas

So one material names two images: lightfalloffmap (the radial/aniso falloff gradient) and lightprojectmap (the projected "cookie" — most lights use a plain white square, lights/proj_white.tga or lights/squarelight1.tga, but 133 distinct materials include real gobo patterns too: lights/projections/spot_leafy, lights/projections/circular_spot_grate/..., lights/projections/venus_audition_projection_slide_1_row, window-shaped cookies lights/spot/c01p1_farm_window01/02, etc.). Both images are packed into one shared atlas (lightsatlasmap = _lightimageatlas, the idLightAtlasResource RTTI class, sized by r_imageAtlasLightWidth x r_imageAtlasLightHeight — default 2k x 1k, i.e. 2048x1024; these are 2 of 9 light-system cvars in the whole corpus that are not CHEAT-flagged (full list and table in Sec.5 — fixed this round, see "Pass 1 errors"), addressed per-material by the ...atlasscalebias rect — the same atlas-rect encoding r2_maplightstairs.md already proved for lightmaps, just a different atlas.

For modding: reusing one of the 133 existing lightMaterial values on a new idLight is a plain text edit (same category of change as every other proven .entities edit in entitypipe.md). Authoring a genuinely new falloff/cookie image would mean adding to the shared atlas — not attempted or needed this round (the kit's 12 lights all reuse two retail materials verbatim via donor transplant, see Sec.7) and not evidenced either way; flagged as an open question, same shape as r4_materials.md's open question about the virtual-texture/megatexture append path.

The GPU-side shape a light actually becomes, read from its renderParm declaration this round:

renderParm lights             { StructuredBuffer light_t view }
renderParm clusterLightsId     { StructuredBuffer uint view }
renderParm clusterNumLights    { StructuredBuffer clusterNumLights_t view }
renderParm numLights           { Vec 0 }
renderParm clusteredLighting   { Vec 0 view }
renderParm lightMask           { Vec 1 }                      -- no scope keyword given
renderParm lightFalloffMap     { String lights/squareLight1.tga }   -- capital L
renderParm lightProjectMap     { String lights/squarelight1.tga }   -- lowercase l (fixed this round, was mistranscribed as squareLight1.tga)
renderParm lightsAtlasMap      { Tex2D  lights/squarelight1.tga view }
renderParm skiplightprobe      { Vec 0 bool }                        -- no scope keyword -> instance scope; probe-bake opt-out only

struct light_t {
    float3 pos;        uint  lightParms;    float4 posShadow;
    float4 falloffR;   float4 projS;  float4 projT;  float4 projQ;
    uint4  scaleBias;
    float4 boxMin;     float4 boxMax; float4 areaPlane;
    uint   lightParms2; uint colorPacked; float specMultiplier;
    uint   shadowBleedReduce_lightScattering;
}

lights/clusterLightsId/clusterNumLights/clusteredLighting are all declared with view scope — the same scope keyword r2_maplightstairs.md used to prove lightmapScaleBias is instance-scoped (set per draw call from the .proc table). view scope means these buffers are bound once per frame/view, independent of which material or which "ambientprogram" variant (outside, outsideUnique, …, r4_materials.md Sec.1.3) a given surface's shader uses — any forward-shaded pixel shader that declares lights/clusterLightsId reads the same frame-global light list and cluster-index buffers. lightMask (Vec 1 = "affected by all lights" by default) and skiplightprobe (Vec 0 bool = probe-bake-only opt-out, affects LIGHT_PROBE sampling, not direct point/spot lights) are the two renderParms that could, in principle, let a surface opt out of dynamic lighting. Fixed this round (see "Pass 1 errors"): pass 1's evidence for "nothing opts out" was 0/11,469 retail materials overriding lightMask — but neither renderParm carries a scope keyword in its decl, which by r2_maplightstairs.md's own cited rule means both default to instance scope, i.e. per-entity data, not material text — so materials were the wrong corpus to search. The right corpus is entity data: round2_checks.py greps the raw text of every entity, all classes, across all 39 retail .entities maps, case-insensitive, for lightmask and skiplightprobe — 0/0 hits for both, independently reproducing and correcting pass 1's conclusion with the corpus its own scope rule actually calls for.

Not decompiled (no shader bytecode disassembler in this toolkit, the same limit r4_materials.md recorded for ambientProgram/stageProgram): exactly how a given pixel shader combines the light_t buffer lookup with a sampled lightmap texel inside one shader invocation. The view-scope argument shows the data is available to every program; it does not show the arithmetic that combines it.

4. castShadows and the shadow pipeline

5,344/13,406 (40%) of corpus idLight instances set castShadows explicitly (4,984 true, 360 false); the rest rely on a C++-side default that is not visible in any decl (light/point/light/spot only set lightType, confirmed by reading all four base decls fresh this round — see Sec.7's donor evidence: the retail point-light donor used by the kit build never sets castShadows at all, while the retail spot-light donor sets it true). Not decompiled: the actual C++ default when the field is absent. Shadow-quality/budget levers found as entity fields: maxShadowVisibleRange (2–40, no single dominant value), shadowZControl. shadowMinNear (0.05–1), shadowRate, shadowResolutionQuality, shadowMipBias, shadowFlags (one value seen corpus-wide, SHADOWFLAGS_NO_ADAPTIVE_MIP), radiosityShadows, backFaceShadows.

5. Budgets/limits found in code (cvars; re_probes/cvartable/cvars_tnc_v2.json, 3,256 cvars, live-read flags/defaults/ranges)

TNC uses clustered forward shading (confirmed by the clusterLightsId/ clusterNumLights/clusteredLighting renderParms in Sec.3, not just inferred from cvar names): the view frustum is divided into r_clusteredLightingTilesX x Y x Z = 16 x 8 x 24 = 3,072 cells (all three CHEAT+SHADERSYNC, not settable at runtime without a shader recompile sync), r_clusteredLightingNearZ/FarZ = 2.0/256.0 pseudo-depth range for the Z-slice distribution. No single "max N lights total" or "max lights per cluster" cvar was found (3,256 cvars checked by regex over name+description for light, 122 hits this round, re-run fresh — absence noted, not a claim that no such cap exists in code — a fixed-size GPU buffer almost certainly has some upper bound, just not one exposed as a cvar). Fixed this round (verifier's missed item): pass 1's "only the tile grid + 2 Umbra caps are quantized budgets" undersold what the same 122-hit sweep actually turned up — real per-frame culling/throttling levers beyond the static tile grid: r_skipLightRangeCulling/CPUCulling/GPUCulling (lights are distance-, CPU-MVP- and GPU-occlusion-culled every frame, each switch defaulting to on, i.e. culling active), r_shadowMaxStaleFrames (throttles how often a spot/point light's shadow map re-renders, per mip level), r_shadowOcclusionMinRadius (10 — above this radius a light's shadow updates get occlusion-culled), and r_shadowDirtyWarningTreshold/ r_shadowTopOffenders (soft-cap diagnostics for "too many lights touch one model" and "most expensive shadow casters"). The handful marked yes above (r_lightClassThreshold, the two light-atlas sizes, r_lightDistanceFade Multiplier, the particle-light-atlas sizes) are EXPOSE+NOCHEAT and should be settable from the normal in-game console without that carrier — not verified this round (no game launch), but consistent with every other EXPOSE/NOCHEAT cvar already confirmed reachable in prior rounds.

6. Dynamic light vs. baked lightmap: relationship, not replacement

r2_maplightstairs.md already proved (code, 123/123 anchors) that every idStaticInstanceEntity in a kind-2 world — which is what every kit piece is — gets the lightmapped "Unique" program unconditionally, and that the only way to avoid that is three hard-coded model-name string compares, unreachable for new content. That round's whole fix (variant H, 927 .proc records) is about making the baked/ambient term plausible. This round's job was the other axis: the direct term. Two cvars make the split explicit as independently-scaled quantities: r_ambientChannelScale ("Scales the ambient light contribution") and r_directChannelScale ("Scales the direct light contribution") — if they were the same pipeline stage, one scale would do. staticLightMapScale (2,770/13,406 idLight instances set it) is the one field that explicitly names lightmap in a dynamic-light's own data — but by name and by its co-occurrence with other clearly bake-time-only fields (contributesToLightProbeGen, staticLightBakeSpecular), it reads as "how much this light contributes when the level is re-baked", not a runtime toggle; this project has no lightmap baker and does not claim to invoke one, so this field is inert for any kit-map light that is only ever loaded, never baked. Put together: a new idLight near the kit should add its direct contribution on top of whatever ambient/baked term the surface already has (0/(1,1,0,0)-sampled before H, a real donor texel after H), through the exact same frame-global lights/clusterLightsId buffers every other forward-shaded surface in the game reads (Sec.3) — inferred from decl/renderParm/cvar architecture, not instruction-level proven, and never seen in the running game.

The kit map itself has no retail lights left to recolor (12/12 are kitmap_light_*, Sec.7 above), so this primitive doesn't apply there, but it is the cheaper route for "tint an existing retail room's lighting" in any other map.

Addlight Usage:
Note: (arg) is required [arg] is optional. Omit the () and []. run addLight -examples for examples
  -point                spawn a point light, defaults to spot
  -spot                 spawn a spot light, defaults to this but at least you know what's happening
  -dist ( n )           spot distance, defaults to 5000, only applicable for spot lights
  -radius ( n )         defaults to 300, only applicable for point lights
  -fov ( n )            defaults to player ( 85 ) fov, only applicable to spot lights
  -intensity ( n )      defaults to 1.0, multiplied into color
  -color ( r g b )      defaults to 1.0 1.0 1.0
  -shadows              turn on shadow casting for this light      -- i.e. OFF unless passed
  -mat ( material )     defaults to nothing, addLight -listMats to see a list of light materials
  -listmats [ filter ]  prints lists of light materials

examples:
  addLight -point -color 1 0 0 -radius 150                                    (tiny red point light)
  addLight -point -color 0 0 1 -radius 500                                    (huge blue shadowed point light -- shown without -shadows in the string dump, read as illustrative, not literal)

This is directly useful evidence, not just a recipe:

  • -shadows is opt-in, off by default — a runtime-level data point (not idLight::Init itself, but the command's own spawn path) consistent with pass 1's open question about castShadows's unset-field default; still not proof of the C++ class default, since addLight could be choosing its own spawn-time default independently of the class's — flagged as INFERRED, not PROVEN, below.
  • -mat defaults to nothing — an addLight-spawned light with no -mat has no lightMaterial override, which (per Sec.3's renderParm defaults) should fall back to the engine's own hardcoded default falloff/ project images (lights/squareLight1.tga / lights/squarelight1.tga), not one of the 133 corpus materials — makes a bare addLight -point -color 1 0 0 -radius 150 a clean, minimal-variable test.
  • The default spawn type is spot, not point (-spot: "defaults to this"), opposite of what the brief's own FIRST PASS example commands might suggest — anyone testing this in game should pass -point or -spot explicitly rather than relying on the default.
  • writeDebugLightmapImage ("writes a debug image of the lightmap") is a cheap diagnostic the in-game test should run first, on any kit static instance, to confirm the kit's new geometry actually has a non-trivial baked lightmap rect before worrying about whether dynamic lights land on top of it — the verifier's own suggestion, carried into the test plan below.
