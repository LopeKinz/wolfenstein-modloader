In plain wordsIn einfachen Worten

This report catalogues the text definitions of Wolfenstein: The New Order (TNO) for weapons, ammo, damage, enemies and the player. They use the same format and patch method as Wolfenstein II, but TNO has one flat set of 14 archives with no DLC or patch layer, and the loader patches every copy, so the DLC folder trap from Wolfenstein II cannot happen. A real difference: 252 of 255 enemy definitions set their own health, so one shared edit cannot reach all enemies, while the aim spread of 26 of 29 enemy weapons can be changed with just 10 edits. Everything is static: the patcher applied 8 installed mods cleanly to the real archives, but the game was not launched and none of the three mod designs was tried.

  • 'set' edits can only change values that already exist; adding a new field, as the aimAssistRange mod does, needs a full file replacement.
  • 252 of 255 enemy definitions set their own health, so a health mod needs a generator over all 252 entries; the TNC-style single shared edit fails here.
  • Editing spread in 10 enemy weapon definitions reaches 26 of 29 through inheritance (correction: pass 1 said 10); whether spread really controls hits is not confirmed.
  • Adding brand-new entries to a TNO archive is still open with no tool yet; the end of each entry was decoded as 9 zero bytes plus an ID unique per chunk and type for definition types.
  • Static only: 8 installed mods were patched cleanly (377 assets), but the three designs (health slider, full arsenal from chapter 1, accuracy slider) are untested in game.

Round-6 research pass on The New Order's decl system: a field catalogue for weapon, ammo, damage, AI and player decls, what the loader can already change, whether brand-new (type, name) entries can be added to a TNO archive, and whether TNO has TNC-style load-order traps. TNO uses the same decl dialect and patch mechanics as TNC but a simpler single-tier archive, and the loader patches every duplicate copy, so the TNC dlc_0 precedence trap does not exist; instead, almost every AI decl overrides health individually. Three TNO mod designs are included. Static only; no game was launched. The append-entry writer this round could not build follows in Adding new entries to TNO archives (R7).

Track tnodecls, round 6, 2026-10-01. Scope: TNO only (<Steam library>\steamapps\common\Wolfenstein.The.New.Order, id Tech 5, WolfNewOrder_x64.exe, 14 chunkN.index/chunkN.resources pairs via master.index, no DLC/patch tier at all). Read-only against the game install and every project file except this track's own folder re_probes/tnodecls/ and this report. The game was not launched, no debugger attached, no process touched. TNO has no runtime image (unlike TNC's re_probes/runtime_87400/module.bin + tools/decomp.py) — every claim here about what the engine does with a decl field comes from the shipped decl text itself, from docs/*.md's own prior binary-string findings (never re-derived), or from this project's own patcher code (wolfsdk/resources.py, wolfsdk/patch.py, wolfsdk/decl.py) and the archive bytes it reads/writes. No disassembly was done this round; where a TNC report's method (tracing a field into .text) would have settled a question, it is flagged as not settleable without a TNO runtime image, not silently skipped.

Built on, not redone: docs/moddingflaeche-tno.md (full corpus census, 105 types, 25 559 parsed text decls, the gamemodesp/faction/enigma cheat routes, startingInventory, 20 largest unused types) — treated as ground truth and cited, not re-measured, except where I independently re-verified a specific field against the pristine backup (see §0). Answer in one paragraph

TNO's decl system is the same dialect and the same patcher mechanics as TNC (confirmed directly: aiHealth.components.components[0].max/cur, actorEditable.damageGroups with 13 zones, faction.myFaction, startingInventory.item[].{startSlot,inventoryDecl} all exist byte-for-byte under the same paths in TNO's entityDef:ai/enemies/default and entityDef:player/game/wolf/*), but the archive container is a different, simpler, single-tier format (chunkN.index, no DLC/patch layering) and the loader already patches every one of the 14 chunks for every duplicate copy of an asset (Installation.find()/apply(), confirmed by code read, §2), which removes the TNC-style "wrong archive wins" trap entirely — there is no equivalent of TNC's dlc_0 precedence to get wrong, because TNO has no DLC/patch tier to begin with (§4). What TNO does have, and TNC's corpus doesn't share, is a structural AI trap: where TNC can flip HP for 125 enemies by editing one shared root decl (soldier_base), TNO's AI decls override aiHealth individually in 252 of 255 corpus entries (measured, §1.4) — there is no cheap single-point health lever, only a generator-script lever. The loader's set mechanism can only touch paths that already exist in a decl (wolfsdk/decl.py:apply_patch raises DeclError on an unknown path) — inserting a genuinely new field (as zielhilfe_alle does for aimAssistRange, confirmed absent from the pristine projectile/handgun, §0) requires a full "file" replacement, not set. Adding a brand-new (type, name) entry to a TNO archive has no code path in this project (resources.py's rebuild() explicitly rejects any payload whose key matches no existing entry, §3) and was never attempted here — but the format itself looks more tractable than TNC's IDCL: no header hash chain, no checksum anywhere, and this round's own measurement (§3, re-verified across all 14 chunks in round 2 after the verifier caught an overgeneralized version of this claim) confirms docs/formats.md's guess that the mysterious 13-byte entry tail is 9 zero bytes + a BE u32 ID, unique per chunk per type for decl-ish types (not globally, and not for audio/particle types) — a concrete, previously-unverified fact, but turning it into a working "append a new entry" writer, round-tripped through the game itself, is out of this round's scope (no runtime image to validate against, and the task's time budget does not cover building and testing a second archive-format writer from scratch). Three ready-to-build designs follow in §5, each scoped to mechanisms already proven safe by the existing mods: a corpus-wide AI-health scaler (252 set edits, generator script), a "full arsenal from chapter 1" loadout swap (one file replace, using retail's own late-game array as the exact donor text — zero guessing), and a 10-decl AI-accuracy slider (set on accuracySettings[].spread, the one true single-point AI combat lever this round found).

Pass-1 errors (fixed in round 2)

The verifier ran an independent re-check and found three real defects in pass 1. All three are now re-verified with broader, fresh measurements (all 14 chunks, not just chunk1/chunk1.index's 40-sample spot check); details are inline at each affected section (§1.1, §3), and the corrected PROVEN/INFERRED lists below reflect the fixes. Short version:

  1. §3's tail-id claim was overgeneralized. Pass 1 said "the 13-byte entry tail is 9 zero bytes + a BE u32 id that increments by exactly 1 between successive same-type entries" as a blanket fact, checked on 40 consecutive entityDef entries in one chunk. Fixed: re-measured across all 14 chunks, every type, with re_probes/tnodecls/probe_tail_v2.py through _v5.py. The claim holds — but only per chunk, and only for decl-ish types (entityDef, weapon, damage, ammo, projectile, aiBehavior, material, trackingParms, faction, gamemodesp, soundmixing: zero within-chunk id collisions in all 14 chunks, every type). It is false for sound/particle/renderProg/cuttableResource (real same-chunk, same-id duplicates — e.g. 50 sound entries all named weapons/smg/ai/smg_ai_fire_nearmid sharing id 111 in chunk1), and the verifier's own counter-claim ("ZERO duplicates… even stronger than the report's own check") was also wrong as a blanket statement — it silently combined ids across all 14 chunks, where the same id value legitimately recurs for unrelated content in different chunks (the id's real scope is per-chunk, not global — see §3). The verifier's specific counter-examples (sound, particle, renderProg, cuttableResource showing duplication) are independently confirmed correct. cm is clean in 11 of 14 chunks and near-clean in the rest (2 dup entries out of 983 in one chunk) — closer to the decl-type behaviour than to sound's.
  2. §1.1's negative control didn't check inherit =. Pass 1 classified the 19 weapon/ai/* decls lacking their own accuracySettings[].spread as "melee/static, no spread concept" by presence/absence in the decl's own text only. Fixed: re_probes/tnodecls/probe_weaponai_inherit.py resolves every one of the 19 decls' inherit = chains. 16 of 19 cascade to one of the 10 spread-bearing base decls (e.g. submachinegun1946 → assaultrifle1960, pistol1946 → pistol, shotgun_lefthand → shotgun); only weapon/ai/baton and weapon/ai/fists/supersoldat1946 are genuinely melee with no inherit; weapon/ai/mg46/supersoldat1946 is a real, unexplained standalone exception (60 own fields, no inherit, no spread). §5.3's actual reach is 26 of 29 weapon/ai/* decls, not 10 — corrected below.
  3. Minor: §5.2 described c01p1's pristine knife as plain weapon/knife; the real value is weapon/knife46cutonly (confirmed by direct re-read). Does not change the recipe (a full-block replace), only the description — fixed below.

New this round, not in the verifier's list (answering its "missed" items and pushing the open questions further): the unexplained 154 probe_tail.py mismatches are now explained (narrowing the search window from 64 to 256 bytes drops the all-14-chunks total from 30 506 to 2 793, and 100% of what's left is type sound — the window was simply too narrow, exactly as the verifier suspected, §3); and docs/formats.md's open "Zähler A" ("counter A") question is now substantially resolved, not just left open: counter A equals the number of distinct (type,name) pairs in that chunk, confirmed exact in 12 of 14 chunks and off by ≤16 (<0.1%) in the other 2 (§3).

2. What the loader can already change — proven by the installed mods

Not re-explained (each mod's own description in mods/*/mod.json already states its mechanism); what's new here is independently confirming, via _wolfsdk_backup/journal.json, that all 8 currently-enabled TNO mods applied cleanly against the real archives: "missing": [], "state": "applied", 377 distinct (type,name) assets written, all 14 chunks rebuilt (0 fit in-place — every touched chunk needed a full Archive.rebuild(), not write_in_place(); expected when several mods touch many small decls scattered across a chunk, each individually too large or too small to fit its own slot via deflate_exact's padding search). This is end-to-end proof the patcher mechanism (not the in-game effect, which the harness's own RUNTIME-PROVEN section already asserts generically for TNO) works against the live archive set, not just in isolated test fixtures.

3. Can NEW (type, name) entries be added to a TNO archive?

No code path exists in this project for it (PROVEN, by code read):

  • wolfsdk/resources.py:Archive.rebuild() builds its payload set only from self.entries (the entries the pristine index already parsed) and explicitly raises ResourceError if any payload key matches no existing entry (missed = set(payloads) - applied, §"rebuild", lines 288–298). There is no insert/append function anywhere in resources.py or patch.py.
  • ResourceIndex is held as its original byte buffer (self.buf = bytearray(buf)) and only ever mutated via set_sizes(), which overwrites 12 bytes at an existing entry's known pos — there is no code that grows the buffer or inserts a new trio + size-fields run.
  • Appending data to the end of a .resources file while leaving the index's entry order unchanged is the exact failure mode docs/formats.md/docs/limits.md already document as measured in a real game launch: FATAL ERROR: idBackgroundLoader::BeginBackgroundLoads: FileTable is out of order. A new entry row placed at the very end of the entry list, pointing at data appended at the very end of the .resources file, would not trigger that specific failure (offsets would still ascend) — but this is reasoning from the invariant's stated cause, not a tested claim, and I did not build or test it.

What this round newly measured, not just inferred (PROVEN, by direct byte read, round 2 widened from 1 chunk/40 samples to all 14 pristine chunks, every type: re_probes/tnodecls/probe_tail_v2.py through _v5.py, re-runnable):

entries (chunk1 alone): 4241   header counters @0x20/0x24: (3508, 4241)
tail length distribution (all 14 chunks): 13 bytes dominates for
  entityDef/weapon/damage/ammo/projectile/aiBehavior/material/trackingParms/
  faction/gamemodesp/soundmixing/cm; "sample" is mostly 37/109 bytes; "sound"
  is mostly 13 bytes but has rarer 133/205-byte tails too (heterogeneous).

docs/formats.md's own hedge — "meist 13 Bytes (9 Nullen plus eine fortlaufende BE-u32-ID)" ("mostly 13 bytes (9 zeros plus a running BE u32 ID)") — is confirmed, with a corrected scope (this is the round-2 fix for the verifier's first finding, see "Pass-1 errors" above): 9 zero bytes, then a BE u32 that behaves as a per-(chunk,type) counter, not a global one:

  • Unique within one chunk, per type, for every decl-ish type checked (entityDef, weapon, damage, ammo, projectile, aiBehavior, material, trackingParms, faction, gamemodesp, soundmixing): 0 within-chunk id collisions in any of the 14 chunks, for any of these types (probe_tail_v3.py). cm is clean in 11/14 chunks and near-clean in the other 3 (at most 2 duplicate entries out of 983 in the worst chunk) — closer to decl-type behaviour.
  • NOT unique across chunks, and this is expected, not an error: the same id value recurs for completely unrelated (type,name) pairs in different chunks (e.g. entityDef id 12189 is ai/tungsten/c03/part_02/soldier_07 in one chunk and breakable/environment/1946_crate_pieces in another; probe_tail_v4.py). Symmetrically, the same name gets a different id in each chunk it has a copy in (e.g. weapon/ai/submachinegun1946: ids {3491, 14445, 17814} across its 3 chunk copies). This answers pass 1's own open question ("unique only within one chunk, or across all 14?"): within one chunk only — a new entry's id only needs to avoid collision with existing ids of its own type in the one chunk being edited, not across the whole 14-chunk install. This also means the verifier's own "independent re-check" claiming "ZERO duplicate ids across all 14 chunks" for these same types was itself wrong as stated — it silently combined ids across chunks, which was bound to show "duplicates" under the real per-chunk-scoped counter; see "Pass-1 errors" above.
  • NOT unique even within one chunk for sound/particle/renderProg/ cuttableResource — confirmed real, e.g. in chunk1 id 111 is shared by 50 sound entries all named weapons/smg/ai/smg_ai_fire_nearmid (probe_tail_v5.py), and chunk0's renderProg has 421 of 846 entries in duplicate-id pairs. These are plausibly variant/take indices into a shared audio-cue or shader-permutation table rather than per-entry unique ids — not traced further, INFERRED only, same caveat as below.

It is not a global file-position counter either way (it jumps discontinuously between type boundaries within a chunk), consistent with a per-(chunk,type) sequential id assigned at content-build time for decl-ish types (plausibly a decl-manager array index the engine fills once per chunk's build, not something resolved by name at load time — this specific mechanism is still INFERRED, not traced into any code, because there is no TNO runtime image to trace it into).

The 154-mismatch question (verifier's "missed" item), now explained: pass 1's own probe_tail.py reported "154 mismatches (pattern not found nearby)" for chunk1 without investigating it. Re-run with the search window widened from 64 to 256 bytes (probe_tail_v2.py, all 14 chunks): total mismatches drop from 30 506 to 2 793, and 100% of what remains is type sound — confirming the verifier's suspicion that 64 bytes was simply too narrow for some tails (consistent with sound's occasional 133/205-byte tails above), not a sign of a different, unexplained format.

Zähler A, substantially resolved (was fully open after pass 1): re-checked the "count of entries whose name is the first occurrence in this chunk" guess directly: counter A equals the number of distinct (type,name) pairs in that chunk, confirmed exact in 12 of 14 chunks (e.g. chunk1: 3508 distinct pairs = counter A exactly) and off by a tiny amount (16 of 15069 in chunk0, 1 of 21400 in chunk2 — both <0.1%, plausibly this project's own resync parser picking up a handful of extra/fewer entries, not a different counting rule) in the remaining 2. Not pinned to 100% exactness in all 14, but strong enough to treat as answered rather than open.

What is still open, explicitly not attempted this round:

  • Whether a hand-built new entry (synthetic trio + size fields + a tail matching this pattern, appended at the end of both the index's entry list and the .resources payload area) is even accepted by this project's own ResourceIndex.load() resync parser, let alone the real engine — not built or tested this round. Building and byte-level self-testing a writer was judged out of scope for the time available (unlike r2_newassets.md's TNC work, which had a runtime image to validate the engine's own lookup path against — TNO has none, so even a working writer here would only prove "our own reader accepts it," not "the game does"). Round 2's per-chunk-scope finding above makes this concretely easier than pass 1 left it: the writer only needs max(existing ids of this type in this one chunk) + 1, not a cross-chunk scan.
  • What a sound/particle/renderProg duplicate id actually indexes (shared cue/permutation table?) — newly measured as real this round, but not traced into any mechanism; irrelevant to the append-entry writer since §5's designs never touch these types.

Net answer: structurally more promising than TNC's IDCL (no checksum, no header hash chain, a resync-tolerant parser), and this round adds real, previously-unverified facts (the tail's exact shape, its per-chunk — not global — scope, and which types the "unique id" property actually holds for) — but turning that into a working append path, proven even at the "our own tooling round-trips it" level TNC's r2_newassets.md reached, is unbuilt and is the single most concrete next step (§6).

4. Inherit / load-order traps — does TNO have a dlc_0-style trap?

No equivalent exists, and the reason is structural, not luck (PROVEN, by code + file-listing read):

  • TNO's base/master.index names exactly 14 chunkN.index/ chunkN.resources pairs, flat, no DLC folders, no patch_*.resources (confirmed: ls of the TNO install root lists chunk0..chunk13 plus master.index and nothing else archive-shaped; contrast with TNC's base/+dlc/dlc_0..5/+patch_1..4.resources tiers that docs/patchvorrang.md/the TNC custom-map memory note are all about). There is no "which layer wins" question to get wrong, because there is only one layer.
  • wolfsdk.patch.Installation.lookup/find() is built once, over all self.archives (= all 14 chunks, always, every apply() call — not a subset chosen per-mod or per-map), and find() returns every hit for a (type, name) key across however many of the 14 chunks carry it (confirmed by code read, §2 above). _apply() then iterates for archive, entry in hits: and writes to every one. Measured duplication is real and non-trivial (§1.4: 444 raw ai/* entries for 255 distinct names, a 1.74× average) — so this "patch every copy" behaviour is load-bearing, not a theoretical safety net: a mod that only patched the first hit would silently leave 189 duplicate AI entries unpatched.
  • The one genuinely open question in this space, carried over unresolved from docs/ladepfade.md Teil 1 (not re-tested here, no game launch): whether fs_overlaypath/loose files in base/generated/ could let a loose file on disk shadow an archived decl of the same path. If that is real, it would be a different kind of trap than TNC's (a loose-file override silently beating an applied archive patch) — docs/ladepfade.md itself says this needs a 10-minute in-game experiment (its own "E1–E3") that was out of scope for a read-only round and still is.

One real trap this round did find, inside the decl layer itself, not the archive layer: the §1.4 "FAILED HYPOTHESIS" above — assuming a TNC-style shared-root AI lever exists in TNO when it structurally does not (252/255 decls override their own health). Anyone porting a TNC AI-difficulty recipe to TNO by analogy would silently affect almost nothing.

5. Three ready-to-build TNO mod designs

All three use only mechanisms independently confirmed safe in §2/§1 above (set on an existing path, or file with a verbatim donor array already shipping in retail) — no new patcher capability required, no new archive entries needed.

5.1 AI health slider, corpus-wide (generator script, set)

What: scale every ai/* entityDef's aiHealth.components.components[0].max and .cur by a constant factor (e.g. ×0.4 for "glass cannon enemies", ×2.5 for "bullet sponge"). Both max and cur must move together — moving only max leaves an enemy's actual spawn HP at the old (lower or higher) cur value, since the decl ships both set to the same number in every sampled entry (§1.4).

Why this needs a generator, not three hand-written edits: §1.4 proved 252 of 255 ai/* entityDefs carry their own override — there is no single shared decl to edit.

Build steps:

  1. Enumerate every (type="entityDef", name starts "ai/") key via Installation.lookup, de-duplicated by name (the loader already patches every chunk copy per §4 — the generator only needs one representative read per name to compute the new value).
  2. For each, Decl(text) (wolfsdk/decl.py), read edit.aiHealth.components.components[0].max/.cur, skip the 3 decls missing the path (§1.4's negative control — set would raise DeclError on them anyway, so skipping is both correct and the cheap path).
  3. Emit one mod.json with ~252 "set" assets: {"entityDef:ai/<name>": {"set": {"edit.aiHealth.components.components[0].max": "<new>", "edit.aiHealth.components.components[0].cur": "<new>"}}}.
  4. No new decl type, no file replacement, no risk beyond what widerstand's 11-asset set edit already proved end-to-end (§2).

5.2 Full arsenal from chapter 1 (file, exact retail donor text)

What: replace entityDef:player/game/wolf/c01/c01p1's startingInventory block (pristine: num = 1, one item, inventoryDecl = "weapon/knife46cutonly" — a chapter-specific knife variant, not plain weapon/knife as pass 1 imprecisely said; corrected this round by direct re-read, does not change the recipe since it's a full-block replace either way) with the exact array already shipping in player/game/wolf/c05_07_09_15/c15 (§1.5):

startingInventory = {
  num = 6;
  item[0] = { startSlot = "BACKPACK"; inventoryDecl = "weapon/knife"; }
  item[1] = { startSlot = "BACKPACK"; inventoryDecl = "weapon/laserkraftwerk"; }
  item[2] = { startSlot = "EQUIPPED"; inventoryDecl = "weapon/assaultrifle1960"; }
  item[3] = { startSlot = "BACKPACK"; inventoryDecl = "weapon/shotgun"; }
  item[4] = { startSlot = "BACKPACK"; inventoryDecl = "weapon/ar60marksman"; }
  item[5] = { startSlot = "BACKPACK"; inventoryDecl = "weapon/handgun"; }
}

Why this is "ready", not just an idea: moddingflaeche-tno.md §4.4 already proposed this exact move in the abstract ("den startingInventory-Block von c16p0 nach c01p1 kopieren", i.e. "copy the startingInventory block from c16p0 to c01p1"); this round turns it into an exact recipe by reading the real retail text of the richest donor (c15, not c16p0 — c16p0 does not exist as a key in the 30-name census, c15 does and is confirmed richer than the next-best c11p1/c14p1 candidates) and confirming every one of its 6 inventoryDecl targets is a real, resolvable weapon decl name (all appear as weapon: entries elsewhere in the same corpus, §1.1/§1.5). Build: copy _wolfsdk_backup's c01p1.decl text verbatim, string-replace only the startingInventory = { num = 1; … } span with the block above, ship as {"file": "assets/entityDef__player_game_wolf_c01_c01p1.decl"} — one asset, zero guessing, matches supersoldaten_c15's already-proven "copy and surgically edit one span" build pattern.

5.3 AI accuracy slider, 10 decls (set, single real combat lever)

What: set every tier of accuracySettings.accuracySettings[0..5].spread to a new value, in each of the 10 weapon/ai/* decls that carry their own copy of the field (§1.1: shotgun, assaultrifle1960, pistol, drone, robot, mg60/supersoldat1960, wol000d_pistol, assaultrifle1960rocket, mechadeathshead_laser, prototyperobot_lkw). Corrected this round (§1.1's inheritance-aware re-check, see "Pass-1 errors"): editing just these 10 decls' spread actually reaches 26 of the 29 weapon/ai/* decls corpus-wide, because 16 more decls inherit the field transitively from one of these 10 (e.g. submachinegun1946 inherits from assaultrifle1960) — only weapon/ai/baton, weapon/ai/fists/supersoldat1946 (genuinely melee) and weapon/ai/mg46/supersoldat1946 (unexplained standalone exception) are unreachable by this design. 10 edited decls, 26 affected — a bigger reach than pass 1 claimed, at the same build cost. Two directions in one mechanism: set all 6 tiers to 0 per decl (enemies hit every shot they take — "deadeye" mode) or scale every tier up by e.g. 2× (much more forgiving aim — an accessibility/easy-mode variant, distinct from the HP-based easy mode in §5.1 and composable with it).

Why this is the clean lever and not trackingParms: §1.4 found TNO's shared trackingparms/aim_default decl has no hit-probability field (parms.item[] is tracking speed, not spread) — the field TNC's doc describes under the same decl type name does not exist in TNO's copy. The actual, verified accuracy knob lives on the weapon side instead, and because weapon/ai/* decls are referenced by name from AI behaviour (not duplicated per enemy instance), 10 edited decls affect every AI that fires one of these 10 weapons corpus-wide — the one genuine single-point combat lever this round found for TNO AI (contrast with §5.1's health, which has none).

Build: 10 "set" assets, each with 6 leaf-path edits (edit.accuracySettings.accuracySettings[N].spread), all paths confirmed present in the pristine decls read this round — no file replacement needed anywhere in this design.

PROVEN

  • TNO's entityDef AI/player decl shape (aiHealth, actorEditable.damageGroups, faction, startingInventory, perkAbilities/perks/upgradeInfo) matches TNC's field paths exactly, confirmed by direct pristine read (§1.4/§1.5).
  • weapon/handgun_base's widerstand diff is exactly 3 hunks, matching the mod's own claimed fields, confirmed byte-for-byte against the pristine backup (§1.1).
  • damage/tungsten/mg46 pristine lacks cuttableRadius/ragdollOnDeath; both exist live, inserted by a "file" edit (§1.2).
  • projectile/handgun pristine lacks aimAssistRange entirely; it exists live (zielhilfe_alle), confirming the loader can insert brand-new decl keys via "file" (§0/§2).
  • 252/255 TNO ai/* entityDefs carry their own aiHealth override; only 3 do not (§1.4, full corpus count).
  • wolfsdk/decl.py:apply_patch() rejects any "set" path absent from the target decl's own parsed values (code read, §2).
  • wolfsdk/resources.py:Archive.rebuild() has no path to insert a new (type,name) entry; it raises on any payload key matching no existing entry (code read, §3).
  • TNO's archive tier is flat (14 chunks via master.index, no DLC/patch layer) and Installation.find()/apply() patches every duplicate copy across all 14 chunks in one call (code read, §4).

INFERRED

  • That the per-(chunk,type) sequential tail id is assigned at content-build time, once per chunk (not resolved by name at load time, and not a single global counter across the install) — plausible from its behaviour (confirmed per-chunk unique, confirmed NOT per-name-consistent across chunks), not traced into any code (no TNO runtime image exists to trace into).
  • That a new entry appended as the last row of both the index's entry list and the .resources payload area would respect the ascending-offset invariant and thus not reproduce the known FileTable is out of order crash — reasoned from the invariant's stated cause, never built or tested.
  • That accuracySettings[].spread is the primary AI hit/miss lever (as opposed to some other, unread field) — supported by it being the only numeric field named "spread"/"accuracy" found on the 10 ranged weapon/ai/* decls (and, transitively, 16 more via inherit), but the actual to-hit math is in the encrypted .text and was not traced.
  • That sound/particle/renderProg/cuttableResource's within-chunk duplicate tail ids index some shared cue/permutation table (rather than being a parsing artifact) — plausible given the duplicate groups share the same decl name (e.g. 50 identically-named sound entries sharing one id), not traced into any code and not needed for any §5 design.

FAILED HYPOTHESES

  • "A TNC-style shared AI-health root decl exists in TNO, so one edit cascades corpus-wide." Refuted by direct count: 252/255 ai/* entityDefs override aiHealth themselves (§1.4).
  • "trackingParms:trackingparms/aim_default carries TNO's AI miss-chance field, the same shape TNC's decl of that name has." Refuted by direct read: TNO's copy has no aimError/trackerRange key, only tracking-speed fields (§1.4). The real lever is the weapon-side accuracySettings[].spread instead (§1.1, used in §5.3).
  • My own first-pass reads of weapon/handgun_base, damage/tungsten/mg46, and projectile/handgun from the live install, initially taken as "what retail ships" — caught and corrected by re-reading from _wolfsdk_backup once the backup folder was noticed (§0); flagged here so the same mistake isn't repeated by a reader skimming only this report.
  • "The 19 weapon/ai/* decls without their own accuracySettings[].spread have no spread concept at all" — refuted by tracing inherit = chains: 16 of the 19 inherit a working spread from one of the 10 base decls; a pass-1 negative control that skipped the exact inheritance check this report itself applies elsewhere (§1.1, verifier-found, round-2 fix).
  • "The 13-byte tail's 9-zero-plus-BE-u32-id pattern increments by exactly 1 and never repeats, full stop" — refuted as a blanket claim: true only per chunk and only for decl-ish types; sound/particle/renderProg/ cuttableResource have real same-chunk duplicate ids (§3, verifier-found, round-2 fix).
