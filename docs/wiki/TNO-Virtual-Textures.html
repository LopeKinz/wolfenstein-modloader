In plain wordsIn einfachen Worten

Wolfenstein: The New Order keeps its large world and material textures in 39 '.pages' files (about 35.6 GB). This page maps the file structure completely: a header, then a tree of texture tiles at different detail levels, and every byte of seven fully checked files is accounted for. The actual pixels inside each tile are stored in a shortened JPEG XR variant that no standard decoder can read yet. So modders can now locate and extract tiles, but cannot yet view or replace the pixels.

  • All 39 .pages files pass the header check; the tile tree is a complete quadtree with one tile at the top and more detail levels below.
  • Seven files were walked completely and every byte was explained, with about 120,000 parent/child links checked without error.
  • Every retail tile uses JPEG XR compression, split into exactly four blocks. That these are diffuse, normal, specular and power maps is a well-supported guess, not proven.
  • The pixel data is not decoded: the block headers lack the normal JPEG XR signature and image size, so a standard decoder cannot be used.
  • About 100 vt_ console settings were found, including ones to change the texture file path or create .pages files; whether they work in the retail game is not verified.

1. The Inventory

<Steam library>\...\Wolfenstein.The.New.Order\virtualtextures\ contains 39 files, totaling 35.6 GB (33.2 GiB; remeasured on 21.09.2026 — the earlier "41 GB" figures here and the "~34 GB" figures in File-Formats.md/Modding-Limits.md were both incorrect and have been corrected). Two families:

Family Example Meaning
cNNpM.pages c13p1.pages, c04p2_3.pages Unique-/Mega-texture per chapter section (World Geometry)
chunkN_vmtr.pages, _vmtr.pages chunk7_vmtr.pages Virtual-Material pages — exactly what materials with usevirtualmapping 1 retrieve (Weapons, Characters, shared assets)

_vmtr.pages is the global vmtr set (1.2 GB); the chunkN_vmtr.pages files correspond 1:1 to the base/chunkN.resources archives.

All 39 files pass the header consistency test (probe_vtpages.py list) without exception:

file                          bytes  across  lvl     nodes  scale  hdr
_vmtr.pages              1201132468    1024   11   1398101      2  ok
c01p2.pages              2962672722    2048   12   5592405      2  ok
c12p1.pages                13563938     128    8     21845      2  ok
...  (all 39: ok)

across ∈ {128, 256, 512, 1024, 2048} — the side length of the virtual texture in pages. It always holds that across == 2^(levels-1) and nodes == (4^levels - 1) / 3, which is the exact node count of a complete Quadtree at this depth.

2. File Header — 32 Bytes (Verified)

Offset Type Value Meaning
+0 u32 0x77339904 Magic (04 99 33 77 on disk)
+4 u32 128…2048 pagesAcross — pages per side at Mip 0
+8 u32 0 zero in all 39 files
+12 u32 8…12 Number of Mip levels (log2(across)+1)
+16 u32 Node count of the full Quadtree (4^levels-1)/3
+20 u32 2 Offset Scale: all offsets/sizes in the tree are in units of 2 bytes
+24 u64 File size in bytes — matches exactly for all 39 files

The scale at +20 is the *_DISK_OFFSET_SCALE value of the engine (the EXE knows PRODUCTION_DISK_OFFSET_SCALE, DEFAULT_DISK_OFFSET_SCALE, UNCOMPRESSED_DISK_OFFSET_SCALE). Retail uses 2 consistently. This was the key to the tree: raw reads yield nonsense offsets, but multiplying by ×2 points exactly to the child sets.

There is no other table, no directory, no trailer. The rest of the file is exclusively the tree.

3. Set Header — 40 Bytes per page (Verified)

Starting directly at offset 32 begins the first set entry. Each entry:

Offset Type Meaning
+0 u32 Magic 0xCABFED04
+4 u32 Compression (idTech5-compression_t), Retail always 5 = COMP_JXR
+8 u32[4] Disk offsets of the four children, in 2-byte units (0 = no child)
+24 u16[4] Reserved size of the four children, in 2-byte units
+32 u32 Page coordinate, packed: x = value & 0xFFFF, y = value >> 16
+36 u32 Mip level, 0 = finest, levels-1 = the single 1×1 root page

Sibling order is row-major: index = (y & 1) * 2 + (x & 1).
For each child, child.x >> 1 == parent.x, child.y >> 1 == parent.y, and child.mip == parent.mip - 1 — verified against ~120,000 parent/child edges with no deviations.

The very first sentence at offset 32 is a special case: compression = 0 (COMP_NONE), containing no payload; both coordinate and Mip are set to 0 and are meaningless. It serves only as the root pointer — its child 0 points to the actual 1×1 page at offset 72. Therefore, it must be filtered out by compression == 0 during evaluation; otherwise, it would be counted as a Mip-0 page.

The four u16 sizes represent what is reserved on the slab, not necessarily what the sentence occupies: the surplus is Slack (see §6).

4. Page Payload — 16 Bytes + Four Channel Blocks (Verified)

Immediately following the 40-byte header:

Offset Type Meaning
+0 u32 LE Magic 0x28190D1E (1e 0d 19 28)
+4 u16 LE Layout code (observed: 0,1,2,4,5,6,8,12,13,14)
+6 u16 BE Size of Block 0
+8 u16 BE Size of Block 1
+10 u16 BE Size of Block 2
+12 u16 BE Size of Block 3
+14 u16 0 in every sentence of all tested files

The four block sizes are big endian — the only field in the entire format. Immediately following them lie the four blocks consecutively, and the payload is padded to an even byte count:

payload_size = (16 + sum(blocksizes) + 1) & ~1

This is not an assumption: sentence size = 40 + payload_size reproduces the file size for c12p1.pages, c16p0.pages, and c03p3.pages byte-for-byte, with no remainder.

Every byte of every tested file is accounted for. The tree is thus confirmed as a model, not merely plausible.

Additional visual inspection: probe_vtpages.py map c03p1.pages 0 --out x.png renders the occupancy of Mip 0. The result consists of clean axis-parallel rectangles of varying sizes — an atlas-packer layout, with no noise. If x/y were swapped or sibling order incorrect, confetti would appear. Typical occupancy: 18% (c12p1) to 34% (c03p1) of pages on Mip 0 are stored at all; the tree is therefore sparsely populated.

Distribution of sentences across Mips, example c02p0.pages (256 pages wide, 9 levels):

mip 0: 18398   mip 3:  727   mip 6:  15
mip 1:  7683   mip 4:  225   mip 7:   4
mip 2:  2413   mip 5:   60   mip 8:   1   <- the 1x1 root page

6. Slack Between Sentences (Partially Open)

Not every file is gapless. c02p0.pages has 739 gaps, chunk3_vmtr 471. Verified:

  • Gaps are reserved by the parent sentence — the parent's u16 size claim exactly covers sentence + gap. The sum of reservation surpluses is byte-identical to the sum of gap lengths.
  • No sentence magic exists within any gap. Thus, the tree reaches everything.
  • The vast majority of gaps are exactly 2048 bytes long.

The content is open. Most entries are 0xFF (free space), but individual bytes within them are deliberately set to 0xE7/0xEF — single deleted bits, which resembles a occupancy bitmap more than filler garbage. In chunk3_vmtr, there are additionally 31 larger gaps (up to ~39 KB) filled with zeros.

Interpretation (Hypothesis, unproven): The Pagefiles are writable. The Engine provides Cvars for this: vt_logPageWrites ("write out log file entries when virtual texture pages are created and written"), vt_stopOnWriteErrors, vt_readOnlyNetPages, vt_createPagesFile. The 2048-byte slack would then be a growth reserve, allowing a newly transcoded page to be rewritten in place at its location, even if it becomes slightly larger.

Source files that the EXE refers to in Assert strings: w:\tech5\engine\renderer\VirtualTextureSystem.cpp, w:\tech5\engine\renderer\jobs\transcode\PageCompression.cpp.

Calculation for the virtualmapping field. A material with virtualmapping = { 0.015625, 0.015625, 0.0, 0.0625 } occupies 1/64 of the virtual texture per axis. In a vmtr file with across = 1024, this equals 16 pages, so 16 × 128 = 2048 texels side length — a completely normal texture size. The first two numbers are thus scaling, and the last two are offset (here: 0 in x, 1/16 = 64 pages in y). The 1024 pages × 128 texels result in a virtual texture of 131072 = 2^17 texels side length, matching the Cvar vt_virtualSizeLog2.

Minor uncertainty: PAGE_PAYLOAD_WIDTH = 120 suggests that a page carries only 128 unique texels and the 4 border texels per page are copies of neighbors. Then the stride would be 120 instead of 128, and the above calculation would yield 1920 instead of 2048. The power-of-two calculation fits better with vt_virtualSizeLog2, but which one is correct remains unproven.

8. The Codec — what is known

Secured:

  • Every Retail set carries compression = 5 = COMP_JXR. No single deviating value in ~145,000 checked sets.
  • Each page consists of exactly four channel blocks, never more, never less.
  • Each block begins with a constant prefix that is bit-identical across all pages and all files:

Block 0: 71 00 a3 c6 0a 3c 60 a3 c6 00 ff 00 00 01 00 Block 1: d1 10 a1 a1 aa 1a 1a a1 a1 a0 ff 00 00 01 00 Block 2: d1 00 8c a3 28 c8 ff 00 00 01 00 Block 3: d1 00 94 25 09 40 ff 00 00 01 00

Blocks 0/1 have a 10-byte header; blocks 2/3 have only 6 bytes. Afterward, all four share the same 5-byte sequence ff 00 00 01 00, followed by variable data. The fact that the header is constant means it encodes only things that are identical across all sides—dimensions (always 128×128) and quantization (set globally via the vt_quality* Cvars).

  • The data section is not a byte-stopped JPEG stream: among 22,238 0xFF bytes in a sample, only 4,893 are followed by a 0x00. Therefore, the standard JPEG FF 00 stop rule does not apply here.
  • The data section is a bitstream. Typical patterns include long runs of 99 99 99…, 66 66 66…, or 49 24 92 49 24 92…—these are periodic bit patterns (10011001, 01100110, 100100100…) produced by an entropy coder when encoding a highly probable symbol repeatedly.
  • The EXE contains the complete symbol table of an HD-Photo/JPEG-XR decoder, verbatim as in Microsoft's reference implementation: WMPHOTO, IndLPLum, AbsLevelIndLP0/1, AbsLevelIndHP0/1, DecIndLPLum0/1, DecFirstIndLPChr, DecIndLPChr0/1, DecNumCBP, DecNumBlkCBP, DecIndHPLum0/1, DecFirstIndHPLum/Chr, DecIndHPChr0/1. (LP = Lowpass, HP = Highpass, CBP = Coded Block Pattern, Lum/Chr = Luma/Chroma—these are the adaptive VLC context tables of JPEG XR.)

Hypothesis (well-supported but unproven): block assignment. Quality Cvars exist for JXR in exactly four variants—vt_qualityJXRDiffuse, …Normal, …Specular, …Power—and there are exactly four blocks. MAX_PAGE_DATA_SIZE_DXT = 16384*5/2 = 40960 decomposes cleanly into DXT1 (8192) + DXT5 (16384) + DXT1 (8192) + DXT1 (8192), and PAGEDATA_IMAGE0_SIZE_DXT = 8192 is exactly DXT1 for 128×128. This matches the measured byte proportions (proportion of total volume per file):

File Block 0 Block 1 Block 2 Block 3
c12p1 40 % 34 % 24 % 2 %
c03p1 26 % 48 % 23 % 3 %
c02p0 36 % 43 % 19 % 3 %
c16p0 29 % 48 % 19 % 4 %
chunk3_vmtr 22 % 63 % 14 % 1 %

Block 1 is almost always the largest (Normal Maps are high-frequency and compress poorly); Block 3 is tiny at 1–4% (Power/Gloss is mostly constant). Therefore: Block 0 = Diffuse, 1 = Normal, 2 = Specular, 3 = Power. The longer header for blocks 0/1 fits the fact that these two are multi-channel while blocks 2/3 are single-channel. This has not been proven.

Hypothesis: the layout code in payload +4. vt_showPageInfo describes itself as "Shows page info: source #, layout #, compression, mono/color specular", and there is vt_maxMonoSpecularError ("specular is considered monochrome if the error is less than this value"). The observed values 0,1,2,4,5,6 and 8,12,13,14 appear to be bit3 = mono specular plus a layout ID 0…6 in the lower bits. The most frequent value is 6.

Open question: the actual decoding. The block header is not a valid JPEG-XR codestream header. A true codestream begins with the 8-byte signature WMPHOTO\0, followed by RESERVED_B=1, flags, and—when SHORT_HEADER_FLAG is set—16-bit width and height. Here, the signature is missing, and there is no room for 32-bit dimensions before the ff 00 00 01 00 sequence (only 6 or 10 bytes total). I additionally searched every bit position of the headers to see if anywhere two identical 16-bit fields with values 127/119/63/31 appear (i.e., 128−1, 120−1, etc.)—no hits.

This means: MachineGames writes a truncated stream. Dimensions and configuration are implicit because they are always identical. A standard JXR decoder cannot process these bytes without first reconstructing the header—and to do that, one would need to know which bits the engine omitted. This cannot be clarified without disassembling PageCompression.cpp code.

10. What This Means for Modding

What is now possible:

  • .pages files can be fully read, indexed, and verified for integrity. One can precisely state which tile resides on which Mipmap level at which coordinate, its dimensions, and its offset within the file.
  • Individual page blocks can be raw extracted (probe_vtpages.py blocks) and compared against others.
  • It is possible to specifically determine which region of a Mega-texture belongs to a given material — via virtualmapping (Scale/Offset) in the Material Declaration and the Occupancy map.

What is not possible: Swapping pixels. This would require an JXR encoder that generates the same truncated stream as MachineGames' encoder. Even with a functioning decoder, the return path would be another project entirely.

Therefore, the more promising paths are not the format itself, but the Cvars:

  1. vt_filePath and vt_filePathVmtrOverride bend the search path. If one reaches a location where complete, custom .pages files can be placed, there is no need to patch the format — only to generate it.
  2. vt_createPagesFile is exactly this generator, built into the game. Together with vt_uncompressedVmtr ("Use uncompressed vmtr data") and the vt_quality* controls, this suggests that the engine still has the encoding side onboard, not just the decoding side.
  3. vt_setSource swaps the Pagefile of a single virtual material at runtime — intended for comparison, but precisely the lever a texture mod would need.

Whether these Cvars are accessible in the Retail build (Console, Cheat flags) has not been verified here. That would be the next sensible step and can be approached with the existing tools (tools/probe_cvars.py, tools/probe_retail_lock.py).

Where This Knowledge Ends

Secured, double-checked:

  • File header (32 bytes), all seven fields, across 39 files.
  • The Offset scale 2 — without it, nothing makes sense.
  • Sentence header (40 bytes): Magic, Compression enum, four child offsets, four child sizes, packed x/y, Mipmap level. Child index (y&1)*2 + (x&1).
  • Page subheader (16 bytes) with four big-endian block sizes.
  • That exactly four blocks exist per page and their lengths.
  • That across seven fully traversed files, every single byte is accounted for.
  • That Retail consistently uses COMP_JXR.
  • The engine constants (128-byte tiles, 4 texel border, 120 usable texels) — these are literally in the EXE.

Speculated, reasoned, but not proven:

  • Block assignment Diffuse/Normal/Specular/Power.
  • Layout code = Layout ID plus Mono-Specular bit.
  • The 2048-byte slack as growth reserve for overwritten pages.
  • Whether the virtual texture edge is across × 128 or across × 120.

Not solved:

  • Pixel data. The bitstream behind ff 00 00 01 00 is not decoded. It is related to HD-Photo/JPEG-XR (the EXE contains the complete HD-Photo decoder), but the block headers are not a valid JXR codestream header — they lack signature and dimensions. Therefore, a standard decoder cannot be attached, and how to correctly reconstruct the header cannot be determined without disassembly.
  • Consequently, no PNG export of a real page. probe_vtpages.py map exports a map (which pages exist, colored by size) — this is proof of the tree structure, explicitly not for the pixel data. A PNG with invented pixels would be worse than none at all.
  • Meaning of individual bytes in the constant block headers.
  • Content and purpose of the gaps partially filled with zeros and bit patterns.
