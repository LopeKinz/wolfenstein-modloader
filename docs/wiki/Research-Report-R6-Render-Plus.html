In plain wordsIn einfachen Worten

This report searched the 3,256 settings of Wolfenstein II: The New Colossus (TNC) for graphics options beyond the Ultra preset and picked 67 that matter, such as shadows, texture streaming, sharpness, foliage, post effects and field of view. Reading the decompiled code proved that one shared function pulls every setting with a declared range (131 of them) back into that range when it is set up or reset; whether a value typed into the console is also limited is still open. From this, two presets ('Ultra+' and 'Clean image') were built for the loader's default.cfg route, while The New Order (TNO) only gets a list of names because its code could not be read. Everything here comes from static analysis: nothing was seen in the running game, and two risks (a stock Ultra config that may overwrite 5 lines at every start, and a possible reset of cheat-flagged settings) are left for the in-game test.

  • Of 3,256 cvars, 304 are exposed; 1,020 carry render or streaming prefixes, and 67 of them were picked as real graphics-quality settings (pass 1 wrongly said 336).
  • Some settings go a step past Ultra, e.g. r_decalFilteringQuality 4 ('Nightmare', 16x) and g_fov up to 120 instead of the default 90.
  • Depth of field, motion blur, chromatic aberration and film grain can be switched off directly without any unlock; only the vignette needs the default.cfg route.
  • No setting gives true supersampling: resolution scaling only lowers the image (floor 0.7, range 0 to 1), and the raw MSAA modes are not recommended.
  • Open and not tested in game: whether the stock initial_video_ultra.cfg overwrites 5 Ultra+ lines at every start, and whether cheat-flagged lines get reset (TNC's reset-message code has no direct callers).

Technical detailsTechnische Details

Der technische Teil ist auf Englisch – so, wie er im Wiki steht. Unterstrichene Begriffe haben eine Erklärung auf Deutsch.

Round-6 research pass on TNC graphics settings beyond the Ultra preset: which registered cvars control render quality and streaming, what range each accepts, and whether each is exposed or cheat-flagged. The report curates the relevant cvars out of the render/streaming-prefixed names, proves from decompiled code that one shared function clamps every cvar to its declared range, and builds two presets ("Ultra+" and "Clean image") for the cfile/resourceExec -s delivery route; TNO gets a names-only catalog. Static only; two open risks (a stock preset cfg that may re-run at every start, and a possible cheat reset) are what the in-game test at the end checks, and it has not been run.

Track renderplus. Scope: TNC is the primary catalog (full decompiled clamp/exposed/cheat evidence). TNO gets a names-only catalog this pass (§1b) — it has no runtime image, so no ranges/clamps/exposed-flags are possible for it, but it does have real render cvar names worth recording, which pass 1 wrongly claimed it didn't (see "Pass 1 errors" below). Read-only on both game installs and on everything outside re_probes/renderplus/ (nothing was written there — this round only read the runtime image, the existing cvar table, the existing cvar-delivery code, and the stock initial_video_*.cfg files) and this report. No game launch, no process attach.

TL;DR

TNC ships 3256 registered cvars, 304 "exposed" (console/+arg-reachable), 2952 not (re_probes/cvartable/cvars_tnc_v2.json, independently cross-checked against the engine's own listCvars dump — see re_probes/agent_reports/cvartable.md, already in the repo, not redone here). Of those, 1020 names start with r_, rs_, vt_, image_, sm_, aa_ or vulkan_ (1033 with fb_) — the render/streaming/ allocator surface (corrected this pass — pass 1 said 336, a ~3× error, see "Pass 1 errors"). Most of that 1020 is aim-assist tuning, SnapMap-portal math and Vulkan-allocator knobs, not graphics quality; §3 below is the curated subset — 67 cvars — that actually match the brief's categories (LOD, shadows, VT streaming, anisotropy, SSR/AO/volumetrics, foliage/decal/ particle, post-FX, FOV, resolution scale, plus image-streaming budgets added this pass in §3.10): exact name, binary default, declared min/max, exposed flag, cheat flag — no guessing, no mining EXE strings.

Three load-bearing facts, all proven from the decompiled runtime, not inferred:

  1. A single shared function clamps every cvar's value to its declared [valueMin, valueMax] whenever a value is parsed from a string (registration, reset, and the runtime name value console path all funnel through it) — found, decompiled and read at RVA 0x1238730 (thousands of call sites, confirmed with --callers). 131 of the 3256 cvars carry a real declared range; for those, no out-of-range value can ever reach the renderer — the engine silently clips it back and prints idCvar: Init value clamped. For the other ~3125 (everything without a declared range, which is most of the interesting render knobs), there is no cvar-layer clamp at all — whatever downstream code does with the value is the only limit, and that code was not individually traced for every cvar (see §6, "what wasn't done").
  2. exposed=false does not mean "unreachable." The loader already has a proven, working delivery route for exactly this problem (wolfsdk/mod.py: with_tnc_tweaks() + wolfsdk/cvars.py: split_tnc(), landed 2026-10-01, see TODO.md): cvars the console/+arg gate rejects get appended as plain name value lines to the retail cfile:default.cfg, which the engine itself runs via its own resourceExec default.cfg -s at every startup (docs/ladepfade.md:240-253, confirmed against NewColossus_x64vk.exe strings, not guessed) — no manual console typing, no +args. The mechanism (resourceExec drops the restriction level to 0 for any file it runs) is runtime-proven generically (re_probes/agent_reports/r4_consolecmds.md) and for cheat cvars specifically (God, g_infiniteAmmo) — but that proof used two other files (cfile:snapdemo.cfg/snapedit.cfg) fired by a bound hotkey, not default.cfg's own unattended startup exec (corrected this pass — pass 1 said "same file", see "Pass 1 errors" #5). Two risks found this pass that bear directly on whether a default.cfg line actually survives to the rendered frame: the same startup init block also unconditionally execs initial_video_<tier>.cfg from disk (§9), and every non-exposed cvar in both presets is CVAR_CHEAT-flagged (§9). Someone should watch qconsole.log once either way (see §10).
  3. Most "quality" tier cvars (r_SSRQuality, r_SSDOQuality, r_motionBlurQuality, …) already default to their own highest declared tier in the binary — the Ultra preset is very likely just "don't touch the compiled defaults." The real headroom beyond Ultra is in three different places: (a) numeric knobs the Ultra preset doesn't touch at all (VT page locking, shadow query budgets, foliage/decal fade distances, DOF/vignette/grain/CA), (b) a few enums that go one step past the tier named "Ultra" in their own description text (r_decalFilteringQuality: 0 Low … 3 Ultra … 4 Nightmare), and (c) forcing off the one quality-reducing default the binary ships on: r_shadingRateQualityOverride defaults to 5 (adaptive variable shading rate), not 4 (full 1x1 every pixel).

1. Method

  • Source of truth: re_probes/cvartable/cvars_tnc_v2.json (3256 cvars, built and triple cross-validated by an earlier round — re_probes/agent_reports/cvartable.md — from the live idCVarSystemLocal registrar walk in re_probes/runtime_87400/module.bin, matched 304/304 against the engine's own listCvars output). I did not re-derive this table; I queried it (python3 -c "..." against the JSON, no new probe script, nothing written to disk outside the scratchpad).
  • Grouped by prefix (r_ 836, vt_ 115, rs_ 17, image_ 16, sm_ 12, aa_ 10, vulkan_ 14 — aa_/sm_/vulkan_/fb_ turned out to be aim-assist, SnapMap-portal and Vulkan-allocator tuning, not graphics quality, and are excluded below) and then by keyword regex per the brief's categories (lod, shadow/cascade, stream, aniso/filter, ssr/ao/volumetric/fog, foliage/decal/particle, motion blur/dof/chromatic/ grain/vignette/bloom/sharpen, fov, resolution-scale).
  • For the one claim that needed code, not just the table (the clamp mechanism), I used tools/decomp.py on the shared value-parser (0x1238730) and the console name value command path (0x1239f20 → 0x1239140, a tail-call the decompiler couldn't unwind further without more budget — see §6) and tools/tnc_runtime_code.py --xref as a negative control (a cvar's own .data record has zero static references outside its own registration constructor — usage code holds a separately-cached pointer that nothing in this round's budget located, so I did not trace individual usage sites beyond the shared clamp function; see §6).
  • TNO: pass 1 wrongly claimed its strings "carry no render cvars worth a catalog entry" — fixed this pass, see §1b. docs/limits.md (TNO) does document a different, already-measured restriction model (com_allowConsole/cheat-reset gate, not an exposed-cvar gate) — that part was right. TNO genuinely has no runtime image (D:/wolf-decomp is TNC-only, re-confirmed this pass), so no code-level claim (clamps, exposed, declared ranges) is possible for it — but its .rdata/.data strings do carry hundreds of real render cvar names, mined this pass with the project's own pre-existing tno_strings.py (zero new code, zero game launches).

Ran python re_probes/enginelimits/tno_strings.py (already in the repo, unmodified) against WolfNewOrder_x64.exe's .rdata/.data, filtered to the same prefixes as §1. Result: ~1020 unique cvar-like names starting r_/rs_/vt_/image_, spanning every category the brief asked about. Highlights — names (and in one case description text) identical to TNC's own catalog, i.e. the same id-Tech-lineage renderer carried these cvars forward:

TNO string (RVA) Matches TNC's Note

2. The clamp mechanism (PROVEN)

FUN_7ff62d448730 (RVA 0x1238730), decompiled in full. Signature (idCvar *this, bool warnIfClamped). For the INTEGER and FLOAT branches (bit 0x2/0x4 of the flags field at +0x60):

fVar2 = *(float *)(param_1 + 0x64);   // valueMin
fVar3 = *(float *)(param_1 + 0x68);   // valueMax
if (fVar2 < fVar3) {                  // only when a real range is declared
    // clip the parsed value into [fVar2, fVar3]
    if (param_2 != '\0')
        FUN_7ff62d4486b0(s_idCvar__Init_value_clamped___i__m_..., clipped, (int)fVar2, (int)fVar3, name);
}

valueMin=1.0, valueMax=-1.0 is the catalog's own documented sentinel for "no range" (cvartable.md §1) — exactly the fVar2 < fVar3 guard above, read independently from the decompiled branch condition, not copied from that doc. --callers on 0x1238730 returns 3261 UNCONDITIONAL_CALL sites (re-counted exactly this pass), essentially every one of the ~3258 per-cvar init thunks (0x2e8d09, 0x2e8eb0, 0x2e9050, …) plus 0x1239034 (confirmed, called from 0x1238fa0, a plausible Reset-to- default wrapper) — i.e. the clamp fires at registration and at reset.

Correction (pass 1 error): pass 1 additionally claimed 0x123932c as a caller. That address is not a valid function start in the analyzed image (tools/decomp.py 0x123932c → "no function contains this address") and does not appear in the --callers output — removed, not replaced.

Console name value runtime path — downgraded to open, not inferred. Pass 1 guessed the path 0x1239f20→0x1239140 and, unable to unwind 0x1239140, argued "console Set also clamps" by elimination (it being "the only value-parser in the bounded cvar range"). This pass decompiled 0x1239140 directly: it is a near-empty trampoline (void FUN(void) — the decompiler couldn't even recover a parameter list) whose only visible body is one tail call to a single shared target, called from 205 sites scattered across addresses that look like physics, UI and audio code — nothing cvar-specific about it. That's real evidence it's a generic compiler-emitted thunk (likely an RTTI/cast or exception-unwind helper), not evidence it's "the only value-parser in range" — the elimination argument pass 1 built on top of it doesn't hold. Whether the runtime console name value Set path clamps is genuinely open, not proven and not disproven, moved out of §5/INFERRED into §6/open questions.

Consequence for the preset below: every cvar in §4/§5 that carries a declared min/max cannot be pushed out of that range by any cfg line, console command, or +arg — the engine itself refuses and logs a warning instead of corrupting anything. That is the safety net the whole "Ultra+" preset leans on for the numeric pushes.

3. Catalog (PROVEN — table lookup, not inferred)

Format: name | default (binary reset-string) | [min,max] (declared, enforced per §2) | exposed | cheat. "needs cfile" = exposed=False → not reachable as a plain +arg or typed console command (gated the same way g_infiniteAmmo was — cvartable.md §3), deliverable only through the cfile:default.cfg route (§8). "direct" = exposed=True → already reachable as +arg/console and also goes through the same cfile route without any extra plumbing.

6. What wasn't done / genuinely open (honest scope limit)

  • Per-cvar usage sites were not traced. A cvar's own .data record has no static xrefs outside its registration constructor (tnc_runtime_code.py --xref 0x2f35050 on rs_forceFractionX's record → zero refs, confirmed) — code that reads a cvar's value holds a separately-cached idCvar* pointer initialized once at registration, and locating that second pointer's own address (to then xref it) is a per-cvar reverse-engineering task, not a one-shot tool call. This round did it for none of the ~330 render cvars; the min/max clamp (§2) is a cvar-system proof, not per-cvar usage proof. Anything whose on-screen effect isn't independently obvious from its own description text is marked INFERRED or left as an open question, not asserted.
  • No game launch happened (forbidden by the brief) — nothing in this report was seen rendered.
  • Whether the runtime console name value Set path also clamps is now genuinely open (downgraded from pass 1's "inferred by elimination" — the elimination argument's own premise didn't hold, §2). Would need either locating the real Set-path value-parser or a live g_fov 999-via-console test with qconsole.log open.
  • Whether initial_video_<tier>.cfg execs on every launch or only on first-ever run is unresolved by any doc in this project and was not resolved this pass either — docs/ladepfade.md's own evidence tier for its ordering is STRING (binary layout, i.e. the order these filenames' exec-strings sit in one init block), not LAUFZEIT (an actual observed sequence). That the file's own content exactly matches the session snapshot's session_values (previous bullet) is suggestive that some session had it active, but doesn't resolve "every launch" vs "once".
  • Whether a TNC cheat-reset silently wipes cfile:default.cfg-set CVAR_CHEAT cvars before the frame renders is unresolved. The printer-function-has-no-callers finding (§4/§5) is new evidence toward "no", but g_infiniteAmmo's existing proof doesn't close this: that test fired after full load via a hotkey-bound resourceExec, well past any startup-only reset window, while default.cfg itself runs during startup — the one place a startup-only reset would actually matter.
  • TNO's render surface now has a names-only catalog (§1b) — ranges, clamps and exposed-flags remain out of reach without a TNO runtime image, which this project does not have.

7. FAILED HYPOTHESES / explicit dead ends

  • True supersampling (render resolution above native) via rs_*: no cvar does this. The resolution-scale system is a downscale-for-perf feature with its own floor at 0.7 and a self-documented 0.0–1.0 range on the force-fraction cvars. Not included in the preset.
  • Raw MSAA (r_antialiasing 10/11/12) as a quality upgrade over TSSAA: not recommended. The enum exists and is reachable, but nothing in this round confirms id Tech 6's pipeline actually supports MSAA correctly (most modern deferred-leaning renderers of this era don't, without dedicated code paths that weren't traced) — flagged as a risk, not shipped in the committed preset.
  • Doubling r_shadowAtlasWidth/Height to 16384: technically legal (unclamped), but 4× the atlas memory of the 8192² default with zero declared ceiling — flagged risky, not in the baseline preset, offered only as an optional advanced line.
  • DevGUI/render-debug-overlay route: docs/ui-assets.md §5 already establishes devgui sets without a lock warning but does nothing in the retail build (F8/F10 draw nothing) — re-confirmed by reading that section, not re-tested; not a path to any of this report's cvars.

10. Smallest in-game test (for the maintainer)

(Translated from German.)

  1. Merge the two blocks from §8.1 and §8.2 into one .cfg file (or enter them directly as new Tweak entries in wolfsdk/cvars.py under _TNC_GROUPS/"Renderer").
