In plain wordsIn einfachen Worten

This page lists what cannot be changed in Wolfenstein: The New Order (TNO) and why, based on the game's own log file. Many cheat settings are locked in the retail version, and none of five tested ways around the lock worked. It explains two strict file rules the patcher must follow, and shows that decl text files are the way to change damage, health and gore instead.

  • Cvars like g_infiniteAmmo are locked, while g_permaGodMode and g_damageScale are not.
  • Compressed data must end with a sync marker; a normal stream end breaks the whole resource reader.
  • Data in an archive must stay in ascending order, so patches write into the existing slot.
  • A patch of 373 assets loaded and ran for about 48 minutes with zero errors in the log.
  • New 3D models, new weapon textures and movement speed cannot be modded yet.

Technical detailsTechnische Details

Der technische Teil ist auf Englisch – so, wie er im Wiki steht. Unterstrichene Begriffe haben eine Erklärung auf Deutsch.

Everything here is measured, not guessed. The evidence comes from the game log (%USERPROFILE%\Saved Games\MachineGames\Wolfenstein The New Order\base\qconsole.log), which the engine writes on every start. It logs the complete command line, every rejected Cvar, and every error — the most useful tool for modding this game.

1. The Retail Lock

The engine rejects certain Cvars:

WARNING: com_allowConsole CANNOT be set in retail!

Measured via a probe run with the full catalog. Locked include, among others:

ai_damageScale        ai_invulnerable       com_allowConsole    com_skipIntroVideo
devgui                g_AimAssist_Disable_All   g_EnableGore    g_debugGore
g_freeCamSpeed        g_gameDifficulty      g_goreBloodyMess    g_gravity
g_infiniteAmmo        g_playerHealthRegenDelay  g_playerHealthRegenSpeed
g_showThinks          g_useSavegameDifficulty   pm_autoSprint   pm_crouchspeed
pm_jumpheight         pm_noBob              pm_noclipspeed      pm_runspeed
pm_sprintMaxTime      pm_sprintspeed        pm_walkspeed

Not locked and thus fully usable:

g_permaGodMode   g_permaInfiniteAmmo   g_damageScale   g_fov
com_showFPS      g_showHud             g_bloodEffects  pm_togglesprint
r_swapInterval

Notable: g_infiniteAmmo is locked, while g_permaInfiniteAmmo is not.

The current status can be measured at any time — write the catalog as a Config, start, and search the log for CANNOT be set in retail.

The tool for this does not exist in the repository. The list above comes from a manually driven probe run; none of the tools/probe_*.py scripts generate it — probe_cvars.py, probe_cheatvars.py, and probe_retail_lock.py all read only the EXE. "Measured" here means measured once, but not reproducible on demand. The reference to tools/probe_retail_cvars.py in wolfsdk/cvars.py:30 points to nothing.

Two different Nays — Config Lock and Cheat Reset

The warning above is the response to a Config line. From the command line, the same rejection looks different, and this is readable in the log. The run from 21.09.2026, 18:47 (qconsole.log, 4,858 lines) produced with

+com_skipIntroVideo 1 +pm_autoSprint 1 +com_allowConsole 1 +g_showHud 1
+g_EnableGore 1 +g_bloodEffects 1 +g_goreBloodyMess 1

not a single line CANNOT be set in retail, but rather:

325: Resetting cheat cvar: pm_autoSprint
326: Resetting cheat cvar: g_goreBloodyMess
327: Resetting cheat cvar: com_allowConsole
328: Resetting cheat cvar: com_skipIntroVideo

This is the mechanism from Section 2, not from Section 1: The assignment arrives, but the Cheat Reset wipes it out. Practically, the result is the same — the Cvar stands at its default value again on game start. Formally, it is a different path, and whoever searches the command line for CANNOT be set to check if a Cvar gets through is looking at the wrong line.

Incidental finding of the same lines: g_EnableGore was also on the command line, stands in the lock list above — and does not appear under "Resetting cheat cvar". From the command line it survives the reset, unlike g_goreBloodyMess two lines down. Whether it works with that is not stated by the log. Unverified. (g_showHud and g_bloodEffects were also present and are anyway not locked.)

2. Why the Lock Cannot Be Bypassed

Five channels were tested:

Channel Lock Cheat Reset Result
binary.cfg / default.cfg blocked — ✗
+devgui 1 (Cvar argument) bypassed wiped out ✗
+set devgui 1 bypassed wiped out ✗
+exec file.cfg (runs after reset) blocked survives ✗
+toggle devgui bypassed survives Cvar = 1, but no effect

Two mechanisms interact with each other:

  1. The lock only allows assignments from the command line. Configuration files are rejected.
  2. A single cheat reset at startup wipes all CVAR_CHEAT cvars: 326: Resetting cheat cvar: devgui It runs after the command line and before everything else.

The combination is tight: what comes early enough to bypass the lock gets caught by the reset; what comes late enough to survive the reset no longer counts as a command line input.

+toggle actually breaks this logic — toggle is a command and runs late, but it originates from the command line:

494: devgui = 1.000000      (no lock warning)

It serves no purpose. With devgui = 1, nothing happens on F8 and F10. The cvar exists, but the functionality behind it is not hooked in the retail build. The same applies to the console.

And an EXE patch?

Not in the Steam version. The EntryPoint lies in a section named .bind — the SteamStub wrapper. The real .text is encrypted on disk, evidenced by the fact that not a single string has a reference, not even "Command line is: ", which is guaranteed to be used. Removing the wrapper would be copyright removal, not modding.

The GOG version is DRM-free. There, a patch would be normal modding on its own file. Whether it leads to the target is open: The DevGUI strings ("DevGUI Key Legend:", ">Trying to Init DevGUI when its already Init!") are embedded in the binary, so the code is presumably present — but behind the cvar sits at least one more hurdle.

3. The Compression Format — the most important detail

Payloads are raw DEFLATE without a finish. Of the 15,069 entries in chunk0, 14,035 end on 00 00 ff ff, the Z_SYNC_FLUSH signature: The BFINAL bit is not set. The engine knows the usize for every entry and inflates exactly that many bytes — it never expects a stream end.

If one instead writes a stream closed with Z_FINISH (i.e., zlib.compressobj(...).flush() in Python), the following occurs:

380: Load 11168 resources using 14023 of 15069 total resource files
381: WARNING: zlib inflate error
382: WARNING: couldn't read production file for decl 'generated/decls/renderProg/...'
... and from here on, every further resource access fails

A single inflate error disables the entire resource reader. The visible crash occurs afterwards at a completely unrelated location — in this specific case with the Combatknife model, which was never touched.

The fix is one line:

packed = co.compress(data) + co.flush(zlib.Z_SYNC_FLUSH)   # not co.flush()

Tricky about it: Python's zlib.decompressobj reads both formats silently. All byte tests were green, while the output format was wrong. tools/verify_patch.py now explicitly checks that every stream ends on the sync marker.

4. The Archive Invariant

Payloads lie in .resources sequentially on 16-byte boundaries, with strictly ascending offsets (verified: 15,069 of 15,069 entries in chunk0). The engine validates this:

FATAL ERROR: idBackgroundLoader::BeginBackgroundLoads: FileTable is out of order

An earlier version of the patcher appended new data to the file end and redirected the index there. This passed every byte test — round-trip byte-identical, revert sha256-identical — and still caused the game to crash at startup.

Therefore, the Patcher writes today into the existing Slot: Offsets never move. The budget is exactly csize — not csize plus alignment padding. Although up to 15 bytes of padding may exist between two payloads, Archive.write_in_place() does not touch them: a shorter stream would shrink csize, and the Loader would then incorrectly address later entries — symptom No address, error: 487. Shorter streams are therefore padded back to csize and the length field remains intact. Whoever calculates the space for an edited Decl computes csize − own Deflate and no additional bytes (example figures in TNO-Modding-Surface.md §4.1). If a replacement does not fit, the affected Archive is completely rewritten — expensive, but orderly.

Lesson learned: Byte-exact round-tripping is not the same as a valid Archive. tools/verify_patch.py checks the order since then.

And in-game? Measured as of 21.09.2026: An apply with 373 Assets, which all 14 .resources files rewrote, started 15 seconds later and ran for approximately 48 minutes until Chapter 12. The qconsole.log from this session contains 0 lines of ERROR, 0 zlib inflate error, 0 FileTable is out of order, and 0 No address. Thus, the Order Invariant holds not only in the verification tool but also in the Loader. This answers the question "does the Engine load the patched Archives without complaint?" — though what the changes do remains unverified.

5. What Cannot Be Modded

New 3D Geometry. md6Def is text, but multimesh.base points to .md6mesh — binary, not examined. A "new weapon" here means: new Decl, existing Meshes, own values, Tags, and Skins.

New Surface Textures for Weapons and Characters. Their pixels lie in the Megatexture (virtualtextures/*.pages, 39 files, 35.6 GB / 33.2 GiB, measured as of 21.09.2026), not as an image Asset — for models/weapons/Handgun/Handgun there is demonstrably no image. Materials with usevirtualmapping 1 derive their data from there. Skins therefore function via bending onto existing materials, not via new image data.

HUD and UI Textures exist instead as image (2,566 pieces). Header Readers, Decoders (BIM → PNG), and Encoders (PNG → BIM) are present — wolfsdk/image.py, exported as wolfsdk image-export and wolfsdk image-import. Two limitations remain:

  • The Encoder writes exclusively Format Code 3 (RGBA8) and requires the replaced image as a template, because multiple header fields are not decrypted. There is no BC1/BC3 compressor — thus a replacement is usually larger than the original and forces an Archive rebuild.
  • Whether a replaced image looks correct in-game is not verified. It is only documented that the Engine loaded four self-built BIMs (Mod wolfsdk.gore_texturen) without writing an error line — see Section 4. Looking at the screen does not confirm this.

Movement Speed, Gravity, Jump Height. As a CVar locked, and no Decl equivalent can be found — a full-text search across all 60,210 text Assets for runSpeed|sprintSpeed|walkSpeed|jumpHeight|gravity yields nothing for the player.

6. What Happens Instead with Decls

The lock applies only to Cvars. Everything the Engine reads from Decls remains untouched:

Desired Effect CVar Decl Path
Weapon Damage — damage/tungsten/* → minDamage, maxDamage
Fire Rate, Magazine — weapon/* → firingIntervals, clipSize
Gore Level locked damage/* → goreTypes, goreBehavior/*
Enemy Health — entityDef → aiHealth.components[0].max
Enemy Weaponry — entityDef → startingInventory.item[0].inventoryDecl
Appearance, Clothing — entityDef → renderModelInfo.model, damageSwapSkin
Weapon Skin — material/* → diffusemap + virtualmapping

Details in modding.md.

7. Open Issues

  • Savegame Compatibility with Player Decl Changes. A run with modified player/game/wolf/chapter_start_default ended in Failed to load md6 model 'combatknife.md6mesh'. Cause unconfirmed; suspected interaction with an existing save state. Anyone working on the player decl should test with a new game.
  • BIM Encoder in Game. The encoder exists (Section 5), but only for RGBA8, and no one has checked whether a replaced HUD image renders correctly.
  • .md6mesh is not examined.
  • Virtual Texture Pixel. The .pages container is decrypted and verified (TNO-Virtual-Textures.md), but the pixel data is not — a cropped JPEG-XR stream, TNO-Virtual-Textures.md §8. Swapping pixels therefore still does not work.
