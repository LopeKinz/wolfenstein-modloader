In plain wordsIn einfachen Worten

This report studies the player systems of Wolfenstein II: The New Colossus (TNC); The New Order (TNO) is only cited from earlier file studies. Basic movement (run, sprint, jump, crouch height) is almost entirely hidden settings, 88 of them starting with pm_, so a movement mod needs the proven resourceExec route; perks, health caps, contraptions and weapon upgrades are text definitions the loader can edit. Perks switch on by themselves when a tracked count such as headshot kills passes a threshold; there are no skill points. The stock developer loadout already hands out all three contraptions (Battle Walker, Ram Shackles, Constrictor Harness) at once. Everything here is static, read from game files and code; only the reused magazine-size edit (pistol 10 to 30) and the resourceExec route were confirmed in game earlier, and none of the three new mods has been run.

  • 18 perk chains of 5 levels each switch on by themselves once a tracked count passes a threshold (e.g. 25 headshot kills); no skill points are spent.
  • Correction of pass 1: headshotter, triggerhappy, secretagent and heavymetal boost all their listed weapons (6, 5, 2 and 4), so no perk data is orphaned.
  • Movement is 88 pm_ cvars, nearly all hidden, so run, sprint and jump values need the resourceExec route proven in game; the exact values in the mod are untested.
  • The stock developer loadout lists all three contraptions together; whether a built-in limit (MAX_CONTRAPTIONS) then cuts this down is still open.
  • The magazine-size edit is confirmed in game (pistol 10 to 30); extending it to other guns, e.g. SMG 45 to 90, and the three mod designs are not tested in game.

Answer in one paragraph

TNC's player tuning splits cleanly into two layers that this track had to tell apart: pure engine state in cvars (all movement — pm_*, 60+ cvars for speed/accel/height/friction per stance, none of them decls, almost all exposed=False so only reachable via the already-proven resourceExec <cfile> -s route, never via +args) and decl-driven player progression (perks, contraptions, weapon upgrade kits, health/armor caps — all plain text, all editable with the loader's proven set/file patch mechanism). The progression layer resolves to 18 stat-gated perk chains (perks/player/sp/<name>_base + _1.._5, 111 decls total with 3 tutorial perks), each chain auto-activating (awardCondition=UC_AUTOMATIC, no manual skill-point spend) once a tracked stat crosses a threshold (requiredStatForActivation.statName/statIncrement, e.g. STAT_KILLS_HEADSHOT +25 for headshotter), and each level pointing at one upgrade:player/perk/<name>_N decl whose modifiersWeapon/modifiersAmmo/ modifiersData list carries the actual number — three real, reflection-visible C++ classes (idUpgradeMod_Weapon/idUpgradeMod_Ammo/ idUpgradeMod_Data, confirmed as qualified Class::ENUM strings in the runtime image) each owning one WMT_*/AMT_*/DMT_* enum. The three "contraptions" the task named are real, corpus-confirmed content (abilityInfo:battlewalker = Battle Walker, abilityInfo:ramshackles = Ram Shackles, abilityInfo:constrictorharness = Constrictor Harness — German Rammbock/Kobra-named internally), each with 3 subAbility0/1/2 + 1 sidequestAbility, granted by giving the player one abilityInventoryItem:abilities/{wanderer,rammbock,kobra} item; a compiled engine constant MAX_CONTRAPTIONS exists (name only, value unread, no runtime instance to query) hinting at a simultaneous-equip cap the game UI enforces, but the stock devinvloadout/code_referenced/default_sp_devloadout decl already lists all three ability items in its startingInventory simultaneously (item[10..12]) — meaning the exact redirect r4_pickups.md already proved for "every weapon" (point a map's world.edit.devmapInvLoadout at this decl) hands the player all three contraptions at once for free, as a bonus this track adds to that finding. Dual wield (r3_newweapon.md's decl-only dualwieldable=true + maxCount=2 finding) gets a fresh runtime cross-check here: the engine carries dedicated RTTI classes idDualwieldAnimAliasVariations/ idAnimSysNode_PlayDualwieldAnim/idAnimSysNodeData_PlayDualwieldAnim (mangled .?AV...@@ names, genuine referenced functions, not just decl text) and a tracked stat STAT_KILLS_DW feeding the triggerhappy perk chain — dual wield is real, wired, deep engine support, not a decl-only illusion. Weapon upgrade kits are a separate system from perks: each weapon decl carries edit.upgrades.item[0..N] naming 2-4 upgrade:weapons/<gun>/<mod> decls (e.g. handgun → magazine_size/silencer/elephantrounds/elephantrounds_silencer), bought with inventoryItem:unlocks/upgradekit currency (a stackable, non-droppable pickup, maxCount=100) at an in-game workbench — the purchase-gating flag itself was not found in static data (likely save-state, out of decl reach), so the safe, already-proven lever is not the upgrade-activation flag but the exact same edit.clipSize field on the base ammo:* decl that tnc-decl-edits.md already confirmed arrives in game (handgun 10→30, proven; this track extends the same lever to smg/battlerifle/shotgun/lkw/dkw, see §6 table). Correction from pass 1 (see "Pass 1 errors" above): three weapon-perk chains that look single-weapon by name (headshotter, triggerhappy, secretagent) are not single-weapon and nothing in this corpus is orphaned — headshotter_N.edit.upgrades already lists all 6 weapon variants (handgun/smg/shotgun/battlerifle/kampfpistol/laserkraftwerk), triggerhappy_N all 5, secretagent_N both of its 2; heavymetal_N was already wired to 4 weapons too. Every one of these perk levels buffs every listed weapon simultaneously, out of the box, in retail — pass 1's "orphaned content, wire it back in" mod idea (§5.4) does not apply; §5.4 is rewritten below to show the real per-weapon value tables instead.

3. Health, armor, regen — decl-driven, proven mechanism

entityDef:player.edit.actorEditable.healthOverrides (num=2) names two healthComponent decls applied at spawn:

item[0] = "player/health_force_100"   -- healthComponent, edit.max=100 edit.cur=100
item[1] = "player/armor_max_100"      -- healthComponent, edit.max=100 edit.component="COMPONENT_ARMOR"

A second, unused-by-default pair already ships in retail: player/health_force_50 (max/cur 50, a "half-health" variant, likely a specific chapter/hardcore-mode override) and player/armor_max_200 (max=200, component="COMPONENT_ARMOR") — the latter is the exact decl the abilityInfo:armorboost ("Repairman"/"Armor Boost" sidequest ability, AT_ARMORBOOST) raises the cap to once unlocked; its abilityInventoryItem:abilities/armorovercharge carries no explicit numeric field itself (just abilityInfo="armorboost"), so the 100→200 swap is almost certainly C++-side logic switching which healthComponent applies once that ability is owned, not a second decl path — INFERRED, not static-provable without the ability actually active in a save. entityDamage:player/testplayerdamage is the player's single damage-group decl (one group "body", one scalar "base" — much flatter than AI's per-bodypart aiHealth structure from r4_aidecl.md; player damage scaling lives in the separate playerdamage/* difficulty-table decls playerEditable.{easy,normal,hard,...}Table already documented by that report's sibling work, not re-measured here).

Regen/decay speed and crouch/stealth-move speed ARE decl fields, via the perk-upgrade chain (§5): DMT_HEALTH_REGEN_SPEED (frontalassault), DMT_HEALTH_DECAY_SPEED (hardysoldier — lower is better, it is the delay before regen kicks in, not a regen rate), DMT_CROUCH_SPEED (assassin), DMT_KOBRA_MOVE_SPEED (kobra/Constrictor Harness prone-crawl speed).

Runtime cross-check: healthOverrides is the one field name in this whole track whose compiled string carries an actual reference (0x7ff62d19ad8b, not inside any disassembled function body — a .rdata reflection-table pointer, same pattern r4_aidecl.md established for aiEditable/perception: "exists as a compiled string with exactly one reflection-table pointer reference, proving the engine's decl-binding schema knows the field"). requiredStatForActivation/autoActivate/ lockedFromStart exist as compiled strings too but with no resolved reference in this snapshot (the x86 Constant Reference Analyzer does not always resolve indirect reflection-table loads — same caveat r4_aidecl.md flagged); their presence as exact-match compiled strings is still evidence, just weaker than a resolved pointer — marked INFERRED below, not PROVEN.

4. Dual wielding — decl mechanism confirmed, now with runtime backing

r3_newweapon.md §1.9 already established the decl mechanism exactly: dualwieldable=true + maxCount=2 on the same weapon decl, no second decl, true for every actually-equippable dual-wieldable weapon (handgun/smg/shotgun/battlerifle variants/kampfpistol). This track adds the runtime side, via python tools/decomp.py --strings:

Three genuine, mangled-name RTTI classes exist purely to drive dual-wield animation blending, plus a confirmed node-index enum for camera-shake and Battle-Walker-combined body reactions — this is deep, dedicated engine support, not a thin decl flag the engine barely reads. The tracked stat STAT_KILLS_DW (feeding the triggerhappy perk, see §5) further confirms dual-wield kills are counted server-side, not just animated.

5. Perks — 18 stat-gated chains, auto-activating, no skill points

entityDef:player.edit.perkCollection lists exactly 21 chains (18 real + 3 tutorial), each {perks.item[0..4] = "perk/player/sp/<name>_1..5"}.
