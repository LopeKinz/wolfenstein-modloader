In plain wordsIn einfachen Worten

This report collects everything in Wolfenstein II: The New Colossus that can serve as a photo mode: a hidden photomode switch, free-camera and time-freeze settings, depth of field, post effects, HUD hiding and screenshot quality. 16 of these settings already work from the normal console; the rest are cheat-locked and need the proven resourceExec route. Reading the code showed that a key bound directly to a locked setting does not work, so the recipe binds keys to small resourceExec files instead, the same trick the sandbox_tools mod already uses for God mode. The resourceExec route itself is confirmed in game, but the photo-mode files and key binds are only static analysis and have not been run.

  • 39 photo-mode settings were checked against the real list of 3,256 settings; 16 of them work from the normal console, such as g_fov, r_dof and g_showHud.
  • Key binds run at the locked level, so a key bound straight to g_freezeTime fails; bound to 'resourceExec <file> -s' it works, as sandbox_tools already proves in game for God mode.
  • Recipe: F9 runs photomode_enter (photomode on, world frozen with a free camera, HUD and crosshair off), F10 runs photomode_exit.
  • No noclip, freecam, photomode or third-person command exists; the camera settings listed for The New Order are only unverified candidates from text strings.
  • Open: what g_setting_photomode 1 does on its own, whether the automatic default.cfg route works in game, and whether devgui 4 opens a window (the one in-game try showed none).

Technical detailsTechnische Details

Der technische Teil ist auf Englisch – so, wie er im Wiki steht. Unterstrichene Begriffe haben eine Erklärung auf Deutsch.

Round-6 research pass on screenshots and machinima in The New Colossus: everything usable as a free camera or photo mode — commands, cvars, kiscule camera nodes and camera entities — and which of it a retail build can reach. The game ships a real, named photo-mode toolkit (g_setting_photomode, a free-camera/time-freeze cluster, depth-of-field, post-FX, HUD and screenshot-quality cvars); some of these cvars are already exposed to the plain console, the rest are cheat-flagged and need the already-proven resourceExec <cfile> -s route. A key bound directly to a non-exposed command does not work, so the recipe binds keys to resourceExec carrier cfgs instead. Static analysis only; the cfg and keybind set has not been run in game.

Read-only on the game installs and on every project file outside this track's own folder (re_probes/photocam/) and this report. Builds on, and does not redo, re_probes/agent_reports/r4_consolecmds.md (the restriction-level gate, the resourceExec level-0 window, the DevGUI call-graph) and r5_kisculecmd.md (kiscule idKisculeNodeCommand's Exec path, the per-frame drain). Ground truth for every cvar/command claim below is re_probes/cvartable/cvars_tnc_v2.json (3256 cvars, live-snapshot-verified) and re_probes/cmdtable/commands.json (234 commands) — not the string-mined candidate lists in docs/cvars-tnc.md/docs/cvars_tnc.json, which that doc's own header says are only ~10% real names. New disassembly this track did itself: RVA 0xaa8780 (key-bind execution) via tools/decomp.py, cross-checked against re_probes/runtime_87400/module.bin. No game was launched, no debugger attached. Every cvar/command/node fact cited below is re-derived and asserted by re_probes/photocam/verify.py (run: python re_probes/photocam/verify.py, prints ALL OK) straight from the ground-truth JSON tables and docs/ghidra/rtti_tnc.json — a mismatch there is this report's own negative control.

Question

TNC screenshots/machinima: everything usable as a free camera or photo mode — camera-related commands/cvars (timescale/pause/freeze, third person, free fly, detach view, viewpos setters like teleport/setviewpos, HUD/viewmodel/ crosshair off, DOF control), kiscule camera/cinematic nodes and camera entities. What works in the retail build (registered + reachable via resourceExec -s or kiscule), and the best possible photo-mode cfg set + key binds.

Answer (short)

The retail build already ships a real, named photo-mode toolkit — it is just locked behind the same console gate r4_consolecmds.md already broke. g_setting_photomode ("enable/disable photomode"), a g_stopTime/ g_freezeTime/g_runFrames/g_freeCamSpeed/cam_cutsceneFreecam free-camera cluster, a full depth-of-field cluster (r_dof* plus a manual com_overrideDOF/com_override_dof_* focus-plane override), a post-FX cluster (r_motionblur, r_vignette, r_filmGrainRatio, r_chromaticAberration, r_hdrShutterSpeed/r_hdrAutoExposure*), a HUD/crosshair/GUI-visibility cluster, and a screenshot-quality cluster (com_captureSamples/com_captureTGA/image_screenshotQuality/ r_screenshotBatchSize) all exist as real, registered cvars (full tables in §4, cross-checked against the 3256-cvar runtime table). A good number of them are already EXPOSEd (g_fov, r_dof, r_dofTAA, r_motionblur, r_motionBlurQuality, r_filmGrainRatio, r_chromaticAberration, r_hdrShutterSpeed, g_showHud, g_showGuis, hud_disableAll, g_showPoiInfo, com_captureFilename/Path/Samples/TGA — 16 cvars, §4 marks each direct) and work from the plain, unmodified console today, no mod needed. The rest — the free-camera cluster itself, g_setting_photomode, crosshair, r_vignette, DOF overrides, screenshot quality, devgui, timescale — are CHEAT-flagged and non-exposed, so they need the already-proven resourceExec <cfile> -s route (project memory tnc-console-unlock.md: runtime-proven 2026-10-01, God/Notarget/ g_infiniteAmmo 1/snapEdit_devMode 1 all executed from a loader-replaced snapdemo.cfg). mods/sandbox_tools/mod.json, already in this repo, demonstrates the exact pattern a photo-mode keybind needs and is itself proven in game: bind F6 "resourceExec snapdemo.cfg -s" — God/infinite ammo confirmed working from a single keypress, no console typing at the moment of the press.

This track's own contribution, new this run: (1) disassembled the key-bind execution function (RVA 0xaa8780) and found it forces the restriction level to 1 for the duration of queuing a bound key's command — unlike kiscule's idKisculeNodeCommand (r5), a key bound straight to a non-exposed cvar will not work; it only works when the bound command is itself exposed, or is resourceExec <file> -s (itself exposed, and which internally re-opens level 0 for its own file — exactly what sandbox_tools already relies on). (2) Found that wolfsdk/mod.py's with_tnc_tweaks() / cvars.split_tnc() already implement a second, automatic delivery route for every one of these cvars: append them as plain lines to cfile: default.cfg, which the engine itself resourceExecs at init at level 0 (idCommonLocal::Init(), r5 §3) — built, round-trip-verified in copies (tools/verify_tnc_tweaks.py, 17/17), but not yet confirmed in a running game (TODO.md, 2026-10-01: "im Spiel unbestätigt", i.e. "unconfirmed in game"). (3) Confirmed the cfile AES-128-CBC encryption is fully solved (wolfsdk/tnccrypt.py, re_probes/agent_reports/cfilekey2.md) and a from-scratch carrier with arbitrary text content and an arbitrary resource name is already built and verified (tools/build_exec_carrier.py) — a photo-mode cfg is not limited to reusing the two unused stock files sandbox_tools found. (4) Surveyed kiscule's camera-adjacent node types (idKisculeNodeActionTeleport 126×, ActionFadeView 55×, ActionRumbleCam 35×, ActionGlobalCameraShake 1×, the ActionMidnightControl/OpMidnightParametersControl cutscene-camera system 958× each) and TNC's compiled-in camera entity classes (idFreeCamera, idUtilityCamera, idSpringCamera, idCinematicCamera, idDeclCameraTrigger, …) — real, RTTI-confirmed, but map/entity placement of these is untested, out of this track's scope. (5) TNO (id Tech 5) has no runtime image; its camera cvars below are string-mined candidates only from a sibling, in-progress track (re_probes/tnoconsole/tno_cmdtable.json), cross-validated only by exact name/description overlap with TNC's proven real cvars — presented clearly labelled, nothing claimed as proven for TNO.

1. The gate, in one paragraph (full mechanism: r4/r5)

One process-wide integer, the "restriction level" (RVA 0x41244d8, idCmdSystemLocal/idCVarSystemLocal shared field +0x200b8). Level 0 = dispatcher (0x1265150) searches all 234 commands/3256 cvars; level 1 = only the 34 exposed commands/304 exposed cvars. It rests at 0 almost all of the time; the console, +args, exec, and the key-bind executor (§2, new this run) each force it to 1 for the duration of one line/keystroke, then restore it. resourceExec <cfile> -s (itself one of the 34 exposed commands) is the one reachable command that forces it to 0 for the duration of the whole file, so every line inside that file — command or cvar, exposed or not — resolves against the full catalogue. Runtime-proven (project memory tnc-console-unlock.md): a loader-replaced snapdemo.cfg run with resourceExec snapdemo.cfg -s printed godmode ON for player 0 / notarget ON for player 0, no "Unknown command", for names absent from the 34-exposed list.

2. New this run: a key bound to a non-exposed command does not work directly

The task asked specifically for key binds, which neither r4 nor r5 settled (r5 explicitly left "does a bound key execute like a kiscule node, or like console input" open). Found it: RVA 0xaa8780 (tools/decomp.py 0xaa8780, called from only one place, 0x11bbe90/0x11bc25f+0x11bc278 — a large input-event function) is the key-bind lookup-and-execute function. Its body:

iVar3 = DAT_7ff6303344d8;              // save old restriction level
... set DAT_7ff6303344d8 = 1 ...       // RVA 0x41244d8 -- the SAME level global r4/r5 use
iVar4 = FUN_7ff62ccb4650(param_1, param_2, param_3);   // resolve key -> binding-table index
for (bound-command list at that index) {
    if (bindset byte matches param_4) {
        if (bound command string is non-empty) {
            AppendCommandText(bound_text);   // via the same devirt-inline pattern as r5 S2
            AppendCommandText("\n");
            ...
        }
        break;
    }
}
...
DAT_7ff6303344d8 = iVar3;              // restore old restriction level

DAT_7ff6303344d8 is confirmed to be exactly RVA 0x41244d8 (0x7ff6303344d8 - 0x7ff62c210000 = 0x41244d8, the live snapshot's image base). This is the identical save/set(1)/restore bracket r4 found for console input, +args, and exec — not the unbracketed-at-ambient-level pattern r5 found for kiscule Command nodes and DevGUI. Consequence: a key bound with bind <key> "<text>" executes <text> at level 1 when pressed, so it only reaches the 34 exposed commands / 304 exposed cvars directly. Binding a key straight to g_freezeTime 1 (non-exposed) will print "Unknown command" the moment the key is pressed, exactly as if it had been typed at the console.

The workaround is the one mods/sandbox_tools already uses and already proved in game: bind the key to resourceExec <file> -s instead. resourceExec is exposed, so it passes the key-bind's level-1 window; its own callback (r4 §3, re-confirmed by r5 §2.1) then force-sets level 0 for the duration of <file>, so every line inside that file — however non-exposed — executes. mods/sandbox_tools/mod.json's own description: "F6 toggles God mode, Notarget and infinite ammo [...] God and infinite ammo are confirmed in game." This is the mechanism §9's recipe is built on.

(0xf515b0, the callback_rva that g_setting_photomode, g_freezeTime, g_debugRenderForceDepthTest all share in the cvar table, turned out to be the generic CVAR_BOOL value-validator, not a "photomode-changed" side-effect handler: its disassembly only compares the new value string against "0"/"1". Correction (pass 1 said "three unrelated BOOL cvars"; a full scan of all 1138 bool-type cvars in the table shows 1136 of them — 99.8% — share this exact callback_rva. It is not a coincidental 3-way share, it is the near-universal BOOL validator; the three named above are unremarkable members of that set. This strengthens the "generic validator, not photomode-specific" conclusion rather than weakening it. Ruled out as a lead, recorded so a later track does not re-walk it.)

3. New this run: cfile:default.cfg already has a built, automatic delivery path

wolfsdk/mod.py (with_tnc_tweaks, TNC_DEFAULT_CFG, _tnc_tweaks_cfile) and wolfsdk/cvars.py (split_tnc, blocked_for("tnc", key) against docs/cvars_tnc_exposed.json, the same 304-name set as cvars_tnc_v2.json's exposed=True rows) already implement: read the retail cfile:default.cfg (decryptable — see below), append every non-exposed tweak as a plain name value line after the retail text, re-wrap and re-encrypt, deploy as one more mod asset. Because the engine itself execs default.cfg at level 0 inside idCommonLocal::Init() (r5 §3, confirmed disassembly), every line added this way runs unfiltered, automatically, at every single launch — no console typing, no key press. This is already wired into WolfSDK Studio's generic TNC cvar-tweak page (_tnc_catalog() loads every name from docs/cvars_tnc.json by prefix; g_→"Game & Cheats", r_→"Renderer", etc. — every cvar in this report's tables is settable there today, though that page's own default-value labels come from the unreliable mined candidate list, not the verified table this report uses).

Caveat, stated plainly: this specific route (cfile:default.cfg auto-applied tweaks) is built and round-trip-verified on copies (tools/verify_tnc_tweaks.py, 17/17 cvars, bit-exact archive round trip, negative control: an all-exposed tweak set never touches the archive) but "im Spiel unbestätigt" (TODO.md, 01.10.2026) — not yet confirmed in an actual running game, unlike the resourceExec <file> -s-at-runtime route (§1/§2), which is runtime-proven. The two routes share the same underlying mechanism (an engine-exec'd cfile at level 0) and the same crypto, so a failure in one would be surprising given the other works — but this track did not launch the game to close that gap itself (out of scope, read-only).

The crypto itself (wolfsdk/tnccrypt.py, re_probes/agent_reports/cfilekey2.md, not this track's own work but load-bearing for the recipe below): cfile payload = u32 declen | 12B salt | 16B IV | AES-128-CBC ciphertext (PKCS7) | 32B HMAC-SHA256 tag; digest = SHA256(salt || "swapTeam\n\x00" || resource name), AES key = digest[:16], HMAC key = digest. Solved and round-trip proven against all 67 retail cfile payloads. tools/build_exec_carrier.py already builds and verifies a brand-new named cfile resource (wolfsdk_test.cfg, arbitrary text "map game/dlc/c02/c2v1_custom\n") in a synthetic DLC chunk that resourceExec would find — so a photo-mode .cfg is not limited to the two unused stock files (snapdemo.cfg/snapedit.cfg) sandbox_tools reuses; it can be its own, clearly-named resource.
