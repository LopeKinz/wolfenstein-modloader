In plain wordsIn einfachen Worten

This page surveys the audio of Wolfenstein: The New Order (TNO) and Wolfenstein II: The New Colossus (TNC). In TNO, the sounds are plain Ogg Vorbis files stored in two big streaming containers, and all sound settings (volume, range, random variants, mixer levels) are readable text declarations. TNC uses the Wwise audio middleware with binary sound banks; WolfSDK can now read them, and a TNC sound replacement is built and enabled in the Studio since release 0.3.0 (not yet tried in game). For TNO, the easiest way to change sound is editing a few text files, not replacing audio data.

  • TNO audio is Ogg Vorbis; all 61,318 sample entries were checked against the streaming containers with 0 mismatches.
  • 99% of TNO sound definitions (9,364 of 9,445) inherit from one master file that adds 10 dB volume, so one number changes almost everything.
  • The TNO mixer file has 13 sub-buses; the player weapon bus sits at -11 dB, a single number in a text file.
  • Replacing actual TNO audio bytes is technically possible but risky: the 1.5 GB streaming containers are not backed up by the tools.
  • TNC uses Wwise with 937 sound banks; a 16-bit PCM WAV can be turned into a game sound, and since 0.3.0 the Studio does this, because Revert now restores replaced sound packs (it was held back in 0.2.0). No sound change is confirmed in game for either game.

1. Which Asset Types Exist

Of 105 Asset Types and 203,843 Assets, seven are audio-related:

Type Count Path Endings What It Is
sample 61,318 .bsnd x61318 Descriptor, no audio data
sound 43,782 .decl x37015, .bsnd x6514, .samplepack x253 Sound Shader (text) + Variant Descriptors
voicetrack 30,627 .bmvtr x30627 Voice Track Descriptor, 4-language
voiceover 2,880 .decl x2880 Selection table over Voicetracks (text)
impactSounds 56 .decl x56 Hit/Shell impact mapping (text)
soundmixing 26 .decl x26 Mixbuses, Gains, Compressor/Limiter (text)
footstepEvents 1 .decl x1 Step Events (text)

The task-named type names soundshader, snd, music, voice, reverb, and soundmaterial do not exist in TNO. What they mean content-wise is located elsewhere:

  • soundshader → this is exactly the type sound; the fields are internally named soundShaderFlags.
  • music → not a type, but a namespace: 225 sound Decls under music/…, e.g., music/menu/main_menu, music/c01p1/mus_c01p1_crashlanding, music/journal/house_of_the_rising_sun.
  • voice → voiceover + voicetrack.
  • reverb → not a type. Reverb is a) a namespace in Sound Decls (weapons/handgun/player/reverb/dw_large_room, …/dw_outdoor, …_rear) and b) the fields wetFalloff, wetVolume, wetMaxDistanceOffset. The Asset Type env (627 items) is Image Environment (Cubemaps, Color Grading), not Reverb — verified against env:default.
  • soundmaterial → does not exist; material references run via impactSounds Decls (metalSound, stoneSound, fleshSound, woodSound, cardboardSound, …).

2. The Actual Data Format

Magic Bytes, all read (Finding):

Type / Ending First 4 Bytes Count
sample/.bsnd b'bsnf' 61,318 (100 %)
sound/.bsnd b'bsnf' 6,514 (100 %)
sound/.samplepack b'1KPS' 253 (100 %)
sound/.decl b'{\r\n\t' (text) 37,009 of 37,015
voicetrack/.bmvtr b'"VTR' 30,627 (100 %)
voiceover/.decl, soundmixing/.decl, impactSounds/.decl, footstepEvents/.decl text all
streamed.resources (1.08 GB) b'OggS' File start
english.streamed (0.39 GB) b'OggS' File start

No RIFF/WAVE, no XMA, no MSADPCM, no Bink Audio (BCF/KB2) in the audio paths. The .bik files under base/bink/ are videos with their own audio track and do not belong to the Sound Engine.

The filenames in the Decls end with .wav — this is the source name from production, not the delivered format. The game uses Ogg Vorbis.

bsnf — the Sample Descriptor

There are two variants, both exactly 74 or 272 bytes in size (no other sizes occur: 33.610 × 74 B, 27.708 × 272 B).

Monolingual, 74 Bytes:

u8[4]    "bsnf"
BE u32   Number of language entries (= 1)
u8[16]   Null bytes
BE u32   @24  Length of the Ogg stream in bytes
BE u32   @28  32              (meaning unconfirmed)
BE u32   @32  Hash/ID
BE u32   @36  0
BE u32   @40  Granule = Number of PCM samples
BE u32   @44  0
BE u32   @48  Length, repetition of @24
--- starting at @52 a WAVEFORMATEX in Little Endian ---
LE u16   wFormatTag        0x674F = Ogg Vorbis Mode 1
LE u16   nChannels         1 or 2
LE u32   nSamplesPerSec    48000
LE u32   nAvgBytesPerSec   192000 (stereo) / 96000 (mono)
LE u16   nBlockAlign       4 / 2
LE u16   wBitsPerSample    16
LE u32   Granule, repetition of @40

Multilingual, 272 Bytes: "bsnf", BE u32 = 4, followed by four 24-byte headers (char[16] language name, BE u32 length, BE u32 offset of the associated 42-byte sub-block within this descriptor), then the four 42-byte blocks starting at offset 104. Observed languages: english, french, italian, spanish.

Example sample:sound/projectile/bullet_impacts/concrete/imp_concrete_01.wav (path generated/sound/…/imp_concrete_01_vorbis.bsnd): Length 17.619 B, Granule 38.822 Samples → 0.81 s, Stereo, 48 kHz.

`"VTR" — the Voicetrack Descriptor

voicetrack:voicetrack/english/ai/efforts/eff_soldier_meleehit_01.vtr is 1.344 bytes in size and contains: Magic 22 56 54 52, BE u32 = 4, four 24-byte language headers (english/french/italian/spanish, each 0x136 = 310 bytes, offsets 0, 414, 724, 1034), then four 310-byte blocks with Magic 22 52 54 56 (`"RTV"). 104 + 4 × 310 = 1.344 — the math adds up exactly. Also no audio data here, only description. Hypothesis: the 310-byte block contains lip-sync/viseme data, because it is too large for simple pointers and the blocks are equal in length per language.

3. Where the actual audio bytes lie — the critical finding

They do not reside in the chunkN.resources. The archives contain only the 74/272-byte descriptors. The Ogg streams are located in two containers that are not listed in master.index:

base/streamed.resources   1.157.177.472 B   begins with "OggS"
base/english.streamed       415.137.488 B   begins with "OggS"

They are addressed via the variable remainder of the index entry — that section which docs/formats.md describes as "longer for audio types, not fully understood". 20 bytes behind the offset/usize/csize triplet stands a BE u32: the byte offset into the container.

Verification across all 61,318 sample entries: for each one, the Ogg page chain was traversed from the indicated offset to the EOS page, and the measured length was compared against the length from the bsnf.

streamed.resources    33,455 entries, length matches exactly
english.streamed      27,863 entries, length matches exactly
                           0 deviations

The container assignment is by name: everything under sound/vo/english/… lies in english.streamed, everything else in streamed.resources.

Slot Grid

streamed.resources   14,454 occupied slots, 14,454 of them on the 16384-byte grid (100 %)
                     free space per slot: min 0, median 8,607, max 3,144,537 B
english.streamed      5,091 occupied slots,  5,091 of them on the 16384-byte grid (100 %)
                     free space per slot: min 0, median 8,041, max 16,380 B

No single overlap. Each sound receives ceil(Länge / 16384) * 16384 bytes. There are fewer slots than entries because the same samples are indexed in multiple chunks.

Answer to the Core Question

The question was: normal archive entries or named resource blocks with pre-calculated size (such as the particles, which failed with idFile_RingBuffer file '<name>.bin' skipping <n> bytes)?

Neither nor — a third case, and it is cheaper than both.

The structural difference from particles is measurable: particle has two entries per asset, 2.672 .decl and 2.672 .bin under the same name. The .bin (Magic 06 54 52 50) is the compiled particle — that is the named resource block at which all particle mods failed. sound has no .bin counterpart. Its .decl entries carry the same short entry suffix (9 zeros + sequential BE-u32-ID) as entityDef, weapon, and material — exactly the types this SDK already successfully patches.

For audio bytes: they are not an archive entry at all, but a piece of file data at a fixed address with a length field located in the archive. The length is therefore changeable, as long as the slot accommodates it.

Inheritance — here lies the lever

99.1% of all Sound Decls (9,364 out of 9,445) inherit transitively from one file:

        parms = {
            volume = {
                offset = 10;
            }
            lfeVolume = -60;

6. What is changeable and what is not

Changeable with existing machinery

sound-, soundmixing-, impactSounds-, voiceover-, and footstepEvents-Decls are ordinary Decl Archive entries without a corresponding .bin counterpart. The existing patch path (wolfsdk/patch.py, deflate_exact, Backup + Journal) applies unchanged, including Revert.

This makes achievable:

  • Volume globally (inheritences/master) or per family
  • Mixbus Gains (soundmixing:default)
  • Range, reverb, lowpass filter, priority, voice count
  • Random selection: more/less variants, redirect to other existing samples — this is the practical way to achieve "other weapon sounds"
  • Music assignment: music/*-Decls can point to other existing music tracks

Hypothesis, not verified in-game: that modified Sound Decls actually take effect. Structurally, everything points this way (same entry residue as the patchable entityDef/weapon), but it has not been verified.

Pitfall: 557 Decls carry an rmsTable for a pre-calculated loudness curve. If volume is increased without adjusting the curve, the HDR audio layer may compensate. Hypothesis. To bypass this, change the gain in soundmixing, which sits behind the HDR stage.

Changeable but without backup — replacing real audio data

Technically, this is the simplest case of the entire project: write an Ogg Vorbis stream to a known offset and adjust two BE-u32 fields (length @24 and @48) plus the granule in the 74-byte bsnf. The descriptor is a normal Archive entry, so it fits into the existing patch path. The slot offers median 8.6 KB of headroom, but for some sounds 0 bytes — a longer stream would overwrite the next sound there.

What argues against this, and significantly:

  1. streamed.resources and english.streamed are not in master.index. Installation.ensure_backup() backs up exclusively the 14 chunkN.index files and records the lengths of chunkN.resources. The two streaming containers total 1.5 GB and are never backed up. A failure would only be fixable via Steam's file verification.
  2. There is no Vorbis encoder in the standard library. New audio must be generated externally — the SDK is fixed to "standard library only".

Recommendation: do not touch this unless the containers are included in the backup. If so, first run ensure_backup to expand the two files and write exclusively shorter streams to keep offset and slot untouched.

Not changeable

  • TNC Audio. The IDCL container format has been read (wolfsdk/idcl.py, verified against all 24 Retail .resources), but the unpacker is not connected and there is no write path. The audio data additionally resides in Wwise Banks for which no parser exists — reading the container does nothing about this. (Superseded 2026-10-04: banks are parsed and a replacement path is built, enabled in the Studio since 0.3.0; sections 9–11.)
  • voicetrack blocks: 310 bytes per language, content undeciphered.
  • .samplepack (Magic 1KPS, 253 items): variant bundles with their own streaming offsets in the entry residue. Not further investigated.

9. TNC Sound Replacement: How a WAV Becomes a Game Sound

Built in WolfSDK Studio; held back in 0.2.0, enabled since 0.3.0, not yet tried in game (section 11).

  • Input: a 16-bit PCM WAV with the game sound's channel count and at most its length (0.01 s slack for export rounding), any sample rate. It stays PCM, the game's other codec: there is no Vorbis encoder here.
  • Output: a PCM WEM laid out like the game's own PCM sounds (fmt tag 0xFFFE, data at offset 64), saved as asset wem:<sound id>.
  • Writing: the loader rewrites every sound pack holding the sound, in every patch level. A loose .wem is replaced whole; in a bank the new slice goes to the end of DATA (16-aligned), its DIDX row is repointed, and the old slice stays unreferenced.
  • Every Sound object (HIRC type 2) of that medium is switched to the PCM plugin 0x00010001, with the size field of its stream type. Measured: the plugin field names the codec: 0x00040001 in all 129,705 Vorbis sources, 0x00010001 in all 409 PCM ones.

Keywords: replace sound, WAV, WEM, Wwise, sound mod, Sound ersetzen, Geräusch austauschen

11. Why Sound and Video Replacement Was Held Back in WolfSDK 0.2.0

Enabled since 0.3.0. In release 0.2.0 the Studio refused sound and video replacements: Revert did not restore the replaced sound packs and video files (the check tools/verify_studio_media.py, "after revert every file of the tree is md5-identical", failed). Since 0.3.0 Revert restores them and the Studio replaces sounds and videos for The New Colossus. Not yet tried in game.

The video replacement is built the same way and was held back with it: a Bink 2 file made with RAD's tools, with the same size and frame rate as the game's video and at most its frame count. The Studio checks it and opens it with the game's own bink2w64.dll; it does not convert. The loose file is replaced whole (asset video:<path>).

Neither path is confirmed in game.
